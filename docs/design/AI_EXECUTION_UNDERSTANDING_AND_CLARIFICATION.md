# AI 任务理解、澄清与执行依据设计

状态：开发中  
日期：2026-08-07

当前进度：前三批核心链路已完成。单任务和批量入口都会立即持久化无工作树的 Run，再由后台完成路由、执行依据准备与物化；未完成的理解 Run、容量等待 Run，以及“工作树已创建但调用未启动”的 Run 都可恢复。配置决策模型时可直接产出任务理解、验收标准、SOP 和风险，未配置时仍使用规则式回退。

## 1. 背景

本地任务始终属于用户；“交给 AI”只表示任务进入 AI 处理阶段。当前流程要求用户先生成完成标准和验收 SOP，再次点击才能真正启动 AI。这会让普通用户误以为第一次操作没有生效，也把本应由 AI 承担的任务理解工作转移给了用户。

本设计将任务理解、验收标准整理和必要的用户澄清纳入同一次 AI Run：用户点击一次“交给 AI”后，任务立即进入 AI 执行生命周期。AI 先理解任务并建立执行依据，只有在需要业务决策、缺少材料或存在风险时才向用户提问；执行依据形成后再开始产生代码或其他实质变更。

## 2. 设计结论

采用“先创建 AI Run，再完成理解和澄清”的流程，而不是在 AI Run 之外增加独立的准备度评估门禁。

```text
本地任务
   ↓ 点击“交给 AI”
立即创建 AI Run，进入“AI 正在理解任务”
   ↓
AI 阅读任务、材料及项目上下文
   ↓
形成验收标准和验证 SOP
   ├─ 内容明确且没有待决事项
   │      ↓
   │  自动冻结本次执行依据
   │      ↓
   │  实施 → 验证 → 交付
   │
   └─ 存在歧义、业务选择、材料缺失或风险
          ↓
      在同一任务中向用户提问
          ↓
      等待用户回复或修改标准
          ↓
      同一个 AI Run 恢复并继续
```

核心约束：

- 点击“交给 AI”后立即创建 AI Run，不要求第二次点击。
- 分析和等待用户回复都属于 AI 执行生命周期，并在“AI 执行”区域可见。
- AI 可以在理解阶段只读检查任务、材料和项目代码。
- 正式执行依据冻结前，不允许修改代码、调用有副作用的工具、发布、合并或创建远程变更。
- AI 建议草案不属于最终审核结果；只有冻结后的执行依据才能用于验证和审核。
- 用户回复后继续原 AI Run，不创建新任务，也不视为重新执行。

## 3. 用户体验

### 3.1 从任务详情交给 AI

用户点击“交给 AI”后，按钮立即变为状态提示：

> AI 正在理解任务。你可以离开此页面；需要确认时会通知你。

页面不要求用户预先填写 SOP，也不再出现“第一次生成方案、第二次开始执行”的交互。

### 3.2 创建并交给 AI

“创建并交给 AI”在服务端完成两个持久化动作：

1. 创建本地任务。
2. 为该任务创建 AI Run。

任务创建成功后立即显示在“我的任务”和“AI 执行”中。即使后续分析失败，本地任务也不会丢失。

### 3.3 AI 主动澄清

只有在用户确实需要作决定时才发起澄清，例如：

- 存在多种合理的产品行为或实现取舍。
- 需要确定兼容策略、回退行为或适用范围。
- 缺少必要账号、文件、接口信息或业务规则。
- 后续动作会产生费用、远程写入、发布或不可逆影响。

AI 应提出一至三个具体问题，并同时说明：

- 为什么需要回答。
- 推荐选择及其理由。
- 各选项可能产生的影响和风险。

不应为了形式完整而询问没有决策价值的问题，例如要求用户再次确认显而易见的测试步骤。

### 3.4 用户可执行动作

等待澄清时，任务页提供：

- 直接回答问题。
- 采用 AI 建议。
- 修改 AI 草拟的验收标准。
- 暂停 AI、保留为人工任务。

建议最多进行三轮澄清。超过限制仍无法形成明确执行依据时，AI Run 停留在“需要人工完善”，避免无限往返。

## 4. 状态模型

AI Run 增加面向用户的执行阶段：

```ts
type AiExecutionPhase =
  | "queued"
  | "understanding"
  | "waiting_for_input"
  | "planning"
  | "implementing"
  | "verifying"
  | "review_ready"
  | "failed"
  | "cancelled";
```

状态含义：

| 阶段 | 用户文案 | 是否允许产生实质变更 |
| --- | --- | --- |
| `queued` | 等待 AI 开始 | 否 |
| `understanding` | AI 正在理解任务 | 否，仅允许只读分析 |
| `waiting_for_input` | 等待你确认或补充 | 否 |
| `planning` | AI 正在制定执行方案 | 否 |
| `implementing` | AI 正在处理 | 是，在隔离工作区内 |
| `verifying` | AI 正在验证结果 | 仅允许验证所需动作 |
| `review_ready` | 等待你审核 | 否 |
| `failed` | AI 执行失败 | 否，可处理失败或重新运行 |
| `cancelled` | 已停止 AI 处理 | 否 |

现有 Work Item 的 `executionState` 继续表达宏观运行状态；新增 `phase` 表达当前 Run 内部阶段。分析中和等待沟通中的任务都计入“AI 执行”，但不应显示为“AI 正在修改”。

## 5. 执行依据

### 5.1 Run 内的执行计划

验收标准、SOP 和澄清记录属于本次 Auto Run，而不是独立评估任务：

```ts
type AutoRunExecutionPlan = {
  status: "analyzing" | "needs_input" | "ready" | "superseded";
  taskUnderstanding: string;
  acceptanceCriteria: Array<{
    id: string;
    text: string;
    source: "issue_explicit" | "body_extracted" | "ai_suggested" | "user_edited";
    confidence: number;
  }>;
  verificationSop: Array<{
    id: string;
    text: string;
    risk: "none" | "low" | "medium" | "high";
  }>;
  openQuestions: Array<{
    id: string;
    question: string;
    reason: string;
    recommendation: string | null;
    risk: "low" | "medium" | "high";
    answer: string | null;
    answeredAt: string | null;
  }>;
  clarificationRound: number;
  confirmedAt: string | null;
  confirmedBy: "ai_policy" | "user" | null;
  contractDigest: string | null;
};
```

### 5.2 自动确认边界

以下内容可由系统自动形成正式执行依据：

- Issue 原文明确写出的 Acceptance 或检查清单。
- 不改变任务业务含义的结构化整理。
- 测试、构建、静态检查、差异检查等低风险验证步骤。
- 从现有项目配置中确定的标准验证命令。

以下情况必须由用户确认：

- AI 新增了影响产品行为的完成标准。
- 存在兼容性、范围、回退方式或用户体验取舍。
- SOP 包含远程写入、发布、合并、费用或不可逆操作。
- AI 对关键要求的置信度不足。

### 5.3 冻结与版本

进入 `implementing` 前生成不可变执行合同：

```ts
type ExecutionContractSnapshot = {
  id: string;
  workItemId: string;
  autoRunId: string;
  version: number;
  workItemRevision: number;
  acceptanceCriteria: string[];
  verificationSop: string[];
  confirmedBy: "ai_policy" | "user";
  confirmedAt: string;
  digest: string;
};
```

每个 Auto Run 记录自己的合同 ID 和摘要。运行开始后修改原任务不会改变该运行的审核依据；若修改内容影响当前任务，应由用户决定继续当前 Run、停止并重新运行，或仅更新后续任务版本。

## 6. 执行安全边界

将现有“缺少执行合同时禁止创建 Auto Run”的门禁后移：

```text
创建 Auto Run
    ↓ 允许
只读理解任务和项目
    ↓ 允许
发起澄清并等待回答
    ↓
冻结执行合同
    ↓
创建工作区并进入实施
```

具体要求：

- `POST /api/work-items/:id/auto-runs` 不再因缺少 SOP 或确认时间而拒绝。
- 初始分析运行在只读权限或无工作区写权限的执行环境中。
- 创建工作树、写文件及调用有副作用的应用前，必须验证冻结合同。
- 合同门禁应位于 `planning → implementing` 的阶段转换上。
- 发布、合并等高风险动作仍使用已有的独立人工审批机制，不能被执行合同自动放行。

## 7. 接口设计

### 7.1 创建 AI Run

```http
POST /api/work-items/:id/auto-runs
```

```json
{
  "agentId": "codex",
  "plannedDate": "2026-08-07",
  "idempotencyKey": "client-generated-key"
}
```

行为：

- 验证任务、项目、Agent 基础可用性和是否已有活跃 Run。
- `plannedDate` 未指定且任务尚未排期时，默认使用当前终端本地日期。
- 创建 `phase = queued` 的 Auto Run，并立即返回。
- 后台 Worker 将其推进到 `understanding`。
- 不要求此时已有正式执行合同。

### 7.2 创建任务并交给 AI

```http
POST /api/work-items
```

```json
{
  "projectId": "project-id",
  "title": "任务标题",
  "body": "任务描述",
  "aiExecution": {
    "agentId": "codex",
    "plannedDate": null,
    "autoStart": true
  },
  "idempotencyKey": "client-generated-key"
}
```

服务端在同一持久化边界创建 Work Item 和待处理 Auto Run，避免出现“任务已创建但交给 AI 失败”且无法恢复的半完成状态。

### 7.3 回答澄清问题

复用现有澄清接口：

```http
POST /api/auto-runs/:id/clarify-answer
```

```json
{
  "answers": [
    {
      "questionId": "question-id",
      "answer": "无效时区回退到 UTC，并保留警告记录"
    }
  ]
}
```

回答保存后，同一个 Run 从 `waiting_for_input` 恢复到 `understanding` 或 `planning`。

### 7.4 确认执行依据

```http
POST /api/auto-runs/:id/execution-contract/confirm
```

请求携带 Run 版本、任务版本，以及用户修改后的验收标准和 SOP。服务端生成合同快照并尝试进入 `implementing`。

## 8. 后台执行与恢复

- Auto Run 创建后进入现有持久化运行队列。
- 服务重启时恢复 `queued`、`understanding`、`planning` 和已回答待恢复的 Run。
- 阶段转换必须幂等，防止重复创建工作树或重复发起问题。
- 通过 `workItemId + activeRun` 限制同一任务只有一个活跃 Run。
- 模型或工具暂时失败时使用现有重试机制，不把基础设施异常误报为“需要用户补充”。
- 用户等待期间释放实际执行进程和计算资源，只持久化 Run 上下文、问题和合同草案。

## 9. 审核结果组织

最终审核页只展示已冻结的正式执行依据：

```text
任务目标
   ↓
本次执行前确认的完成标准
   ↓
每条标准对应的验证证据和结论
   ↓
风险、未覆盖内容和建议下一步
   ↓
审核通过 / 让 AI 继续修改 / 停止交付
```

AI 在理解阶段生成但未被采纳的建议、历史问题和原始技术分析放入“执行过程/专业详情”，不得混入最终审核标准。

## 10. 与现有实现的改造关系

### 服务端

- 保留现有执行合同概念和交付门禁。
- 将 Auto Run 创建时的 `executionContractGate` 后移到进入实施阶段。
- 给 Auto Run 增加 `phase`、`executionPlan` 和 `executionContractId`。
- 调整自动运行 Worker，使其先执行只读任务理解，再按结果继续、提问或等待确认。
- 复用现有 `clarify-answer` 能力保存回答和恢复 Run。
- 现有 `/api/work-items/assist/draft` 仅保留为可选的编辑辅助，不再承担启动 AI 的前置门禁。

### Web

- 首页“创建并交给 AI”不再预先强制填写完成标准和 SOP。
- 任务详情“交给 AI”只需点击一次。
- AI 执行看板展示 Run 阶段，而不是只有运行/失败等粗粒度状态。
- 在任务详情增加澄清问答区域，并直接支持回复、采用建议和停止 AI。
- 审核页使用冻结合同，不展示未采纳草案。

## 11. 迁移策略

- 已有 `executionContractConfirmedAt` 的运行映射为 `legacy-v1` 合同快照。
- 已经完成的历史运行保持原有结果，不使用后来生成的新标准重新审核。
- 尚未执行且缺少合同的任务，在下一次点击“交给 AI”时直接进入 `understanding`。
- 已处于旧版“两次点击”中间状态的任务，可把现有标准作为 Run 的初始草案，但不自动视为用户确认的新合同。

## 12. 交付阶段

### 第一阶段：统一生命周期

- 单击创建 Auto Run。
- 新增 `phase` 并在 AI 看板显示。
- 把合同门禁移动到实施阶段。
- `plannedDate` 为空时默认今天。

### 第二阶段：理解与澄清

- AI 生成任务理解、验收标准和 SOP。
- 增加任务内澄清问答及恢复执行。
- 明确自动确认与必须人工确认的政策。

### 第三阶段：审核闭环

- 冻结合同快照。
- 将完成标准、验证证据和复核结论逐项关联。
- 支持在审核页直接通过、继续修改或停止交付。

## 13. 验收标准

- 用户点击一次“交给 AI”后，任务立即进入“AI 执行”。
- 缺少完成标准时仍能创建 Auto Run，并进入只读理解阶段。
- 未冻结执行合同前不会产生代码或其他实质变更。
- 明确且低风险的任务无需用户二次操作即可继续实施。
- 存在业务决策或关键信息缺失时，AI 在同一任务中提出具体问题。
- 用户回答后恢复原 Run，不创建新任务或新历史运行。
- 分析中、等待回复、实施中和验证中的阶段在看板上可区分。
- 服务重启、重复点击或重复回答不会创建重复 Run、工作树或合同。
- 最终审核仅使用执行前冻结的标准和 SOP。
- 普通本地任务在未交给 AI 前不会自动生成 SOP 或进入 AI 队列。

## 14. 开发计划与当前进度

### 14.1 第一批：交互与兼容链路（已完成）

- 首页“创建并交给 AI”和任务详情“交给 AI”改为单击启动，不再要求先生成草案、再点击执行。
- 未设置执行日期时，由客户端携带当前终端时区，服务端默认排到终端本地当天。
- Auto Run 增加面向用户的 `phase`，看板可区分理解、等待回复、实施、验证和审核等阶段。
- 任务详情可直接回答 AI 的澄清问题；回答后复用同一个 Auto Run 和工作区继续执行，不创建新的历史运行。
- 为兼容现有执行入口，服务端可在交接请求中补齐缺失的验收标准和 SOP，并继续进入现有 Auto Run。

这一批解决“一次点击是否生效”和“去哪里回答 AI”的问题，但最后一项仍是过渡实现：执行草案在 Auto Run 持久化前同步形成，尚未达到第 6 节定义的严格只读阶段边界。

### 14.2 第二批：Run 内理解与工作树门禁（已完成核心链路）

1. 已完成：先持久化 `phase = understanding` 的 Auto Run，记录生成时 `worktreeId` 和 `invocationId` 均为空。
2. 已完成：将本次标准、SOP、风险、来源和确认信息保存到 `autoRun.executionPlan`。
3. 已完成：执行合同冻结前不创建工作树、不启动 Agent 调用；合同门禁位于 `createWorktree` 之前。
4. 已完成：决策为 `clarify` 时只保存“待确认草案”并进入 `waiting_for_input`，不提前冻结合同；用户回答后以用户为确认主体冻结合同，同一个 Run 才进入实施。
5. 已完成：生成带 SHA-256 摘要的 Run 级合同快照；相同请求幂等重放，不允许用不同内容覆盖已冻结合同。
6. 已完成：配置决策模型时，同一次只读后台决策可结合受限项目上下文，返回任务理解、验收标准、SOP 和风险，并作为执行计划草案。
7. 已完成：理解阶段进入后台队列，服务启动和每 10 秒周期扫描可恢复未完成 Run。
8. 已完成：批量调度迁移到同一预留 Run/后台理解链路；容量不足进入 `waiting_capacity`，后续扫描继续原 Run，不记为失败。
9. 已完成：如果中断发生在工作树创建后、Agent 调用前，恢复时复用原工作树，不重复创建分支。

### 14.3 第三批：合同快照与审核证据（待开发）

1. 持久化不可变的 `ExecutionContractSnapshot`，记录 Run、任务版本、确认主体和摘要。
2. 将每条完成标准与验证命令、结果、文件变更和 Codex 复核结论逐项关联。
3. 审核页只显示本次执行前冻结的正式标准；未采纳草案和澄清过程进入“执行过程/专业详情”。
4. 在当前审核页面直接提供“审核通过”“让 AI 继续修改”“停止交付”，并明确每个动作的影响和风险。

### 14.4 第四批：迁移与发布（待开发）

### 14.7 第三批：后台理解、恢复与批量迁移（已完成）

- HTTP 交接只负责校验、持久化和入队，返回 `202`；路由决策也在响应之后执行。
- 后台协调器负责路由、执行草案、确认策略、合同冻结、工作树物化和 Agent 启动。
- 服务启动时恢复遗留的 `understanding` / `planning` Run，运行期间每 10 秒继续扫描。
- 批量任务不再在创建批次时预生成 SOP；每项先创建自己的 Run，再进入同一后台理解流程。
- 全局容量不足不会污染成执行失败，而是保留为 `waiting_capacity`，有容量后继续。
- 决策模型结构化输出支持 `taskUnderstanding`、`acceptanceCriteria`、`verificationSop` 和 `risks`；所有字段经长度、类型和数量校验后才可进入草案。

### 14.8 第四批：受限项目上下文理解（已完成核心链路）

- 后台理解阶段读取根目录文档白名单（如 README、AGENTS、CONTRIBUTING 和主要项目清单），单文件与总字符数均设上限。
- 根据任务标题、正文和反引号标识符，复用项目只读搜索定位最多 20 条相关代码线索；搜索继续跳过 Git 忽略项、凭据文件、二进制和超大文件。
- 同项目内最多引用 5 个相似任务，只带任务标题、状态和已有验收标准，不跨项目取数。
- 项目配置只能选择运维侧白名单中的验证命令；模型不能自行构造或执行命令。
- 文档摘录和代码预览在传给决策模型前再次进行疑似密码、Token、Secret 和 Bearer 凭据脱敏。
- 原始摘录仅存在于当次内存调用，不写入 Run；Run 和执行计划只保存来源路径、计数、验证命令、截断/脱敏说明和 SHA-256 摘要。
- 任务详情以“AI 理解任务时参考了什么”呈现普通用户摘要，并明确这些内容是规划输入，不是完成或验收证据。

第四批保留的降级策略：未配置决策模型或模型暂时不可用时，仍按确定性启发式路由并继续执行；此时项目上下文会保留为可审计摘要，但不会被启发式逻辑解释。后续可增加按项目配置的上下文来源开关与质量指标。
