# 数据驱动任务执行体系：验收复盘与详细开发计划

> 状态：执行中（P0～P4.7 首批能力已落地，真实业务数据试点仍待验收）
>
> 更新时间：2026-08-17
>
> 适用范围：iLink/Channel 自然语言入口、Work Item、Task Thread、AutoRun/Invocation、任务模板、数据上下文、验收与 Evidence。

## 1. 目标

让普通用户像日常安排工作一样使用 MyAgentTool：

> “把这个整理一下” → “按上次的方式再做” → “这个不对，再改一下”。

用户不需要知道任务 ID、模板名称、字段模型、Bridge、Invocation 或内部状态。系统在后台负责：

1. 理解工作目标；
2. 找到相关数据并记录来源；
3. 匹配任务模板或回退到通用任务；
4. 只追问必要信息；
5. 按风险决定直接处理、预览确认或审批；
6. 执行、验证、交付；
7. 在需要时展示完整过程、依据和修订历史。

同时满足专业使用诉求：结果出错时，能够定位是数据、理解、模板、执行还是验收环节的问题，并能修正本次任务或经过确认后改进模板。

## 2. 当前能力复盘

### 2.1 已满足

- Channel 支持自然语言、问候、咨询、新任务、补充、确认、查询、重试、继续、转人工等基础交互意图。
- 连续消息有收集窗口，能够合并文字和附件形成任务草稿。
- Task Thread 已有状态历史、来源事件、任务短引用、队列位置、进度心跳、长时间无进展和人工接管。
- 多任务可以分开建立线程，支持当前任务选择、乱序完成和结果关联。
- iLink 图片、语音、文件可以作为受治理的输入资产进入任务；结果资产可以通过 Channel Delivery 回传。
- Channel 任务已关联 Work Item、AutoRun、Invocation、Delivery 和 Trace。
- Work Item 已支持 acceptance criteria、verification SOP、verification records、completion gate、review contract 和 Evidence UI。
- 已有 My Template 的匹配、学习案例、反馈、草稿、版本冲突和启用确认能力。
- 失败重试、投递重试、重启恢复、取消、暂停/继续和人工接管已有可靠性基础。

### 2.2 部分满足

- Channel 任务能够携带附件和本地项目上下文，但还没有统一的数据来源快照和来源解释。
- Channel 创建任务已接入模板匹配、验收标准和验证 SOP；低置信度匹配仍回退为通用任务，统一数据来源快照尚未完成。
- 开发类任务的验收和证据链较完整；普通 Channel 任务可能没有足够的领域验收标准。
- 任务消息可以追加到现有线程，但还没有清晰的 Task Revision 版本模型。
- 桌面端有任务观察、Invocation 追踪和 Evidence 页面，但尚未把 Channel 事件、任务、执行、交付和修订统一成一个面向用户的复盘时间线。
- Channel 任务已能根据确定性风险信号区分低风险和对外发送、财务、删除/覆盖等高风险路径；具体能力级风险声明和外部连接器仍在完善。

### 2.3 尚未满足

- 物流、报价、库存等外部连接器，以及付款账户的实际登记和同步仍未完成；当前对象校验先覆盖本机已登记的业务实体、文件和发布通道。
- 每次任务的数据快照、版本、读取范围、来源可信度和用户确认记录。
- Channel 任务结果的领域级自动验收，不能只以 Bridge 返回成功作为完成依据。
- “这个不对”后的自动问题归因、局部修订、版本比较和重新执行。
- 将用户对本次任务的纠正，经过明确确认后沉淀为模板规则的完整 Channel 闭环。
- Channel 专属的专业复盘视图和按需专家指导入口。

### 2.4 本轮实施进度

- P0（首批）：已为 Work Item 增加可校验的 Channel 任务合同，包含领域、风险、目标、预期输出、输入来源摘要和模板匹配摘要；旧 Work Item 继续按旧字段读取，不强制迁移。
- P1（首批）：已将 Channel `/task` 创建接入 `suggestWorkItemDraft`，自动生成领域化验收标准和验证 SOP；强匹配模板才冻结版本，其他情况保留通用任务。
- P2（首批）：已为 Work Item 增加来源快照和摘要，记录来源类型、名称、路径引用、版本、哈希、用途和摘要指纹；详情可显示 `current / stale / unknown / empty`。
- P2（首批）：材料增删或版本变化会和已确认快照比较；刷新快照需要显式确认，并保留最近历史快照和审计活动。
- P2（首批）：AutoRun 冻结执行合同时携带来源快照摘要，复盘时可确认执行使用的是哪一版来源。
- P3（首批）：个人 Channel 的高风险任务先创建本地 Work Item 并进入待确认，不直接执行；用户回复“确认执行”后复用桌面端同一条任务路由。
- P3（首批）：支持“确认执行”“取消”和重复确认；确认、取消、路由失败均保留在 Task Thread 和 Channel 事件审计中，不新增意图队列。
- P3.2（首批）：高风险任务生成可读执行预览，包含操作、对象、金额/范围、输入附件、影响和未明确字段，并保存预览摘要。
- P3.2（首批）：用户补充对象或内容时，旧预览、旧待路由请求和旧确认自动失效；重新确认会创建新的任务修订，不复用旧 Work Item。
- P3.3（首批）：预览区分“提示信息”和“执行必填信息”；缺少金额、收款方、付款账户、发送对象、发送内容或删除范围时，“确认执行”只返回补充提示，不会路由。
- P4.0（首批）：新增统一可验证对象层。客户/订单读取 `businessEntities`，文件读取 `workflowArtifacts` 或受治理的 Channel 附件，发布目标读取已启用 Channel 或连接器登记的 `channelObjectRecords`；对象按团队和项目隔离，并保存脱敏摘要、版本/指纹和确认快照。
- P4.0（首批）：高风险任务确认时重新解析联系人、订单、账户、文件和发布目标；对象缺失、歧义、跨团队、停用或版本变化会保持待确认，不启动执行。
- P4.1（进行中）：新增本机业务对象登记入口和 `/api/channel-objects` 管理接口，支持联系人、订单、付款账户和发布目标的团队/项目隔离、版本更新、停用/恢复；账户只保存后四位，不保存完整账号。
- P4.1（首批）：桌面端“我的模板”页增加“业务对象”卡片，普通用户可以用名称和少量辅助字段登记对象，不需要理解内部 ID。
- P4.2（本轮）：Channel 任务合同增加“工作方式快照”。普通用户只看到本次会按什么方式处理、预期得到什么、使用哪些资料以及是否需要确认；专业用户可追溯模板版本、数据计划摘要、关系摘要、执行摘要和快照指纹。临时任务不强行绑定模板，候选冲突会进入待确认。
- P4.2（本轮）：iLink 排队回复会带上已识别的工作方式和队列状态；工作方式随 Task Thread、待确认请求和 Work Item 一起保存，重启或乱序完成后仍能回看同一份理解结果。
- 已补充 Work Item、iLink 组合、任务材料、AutoRun 和 HTTP 测试；当前目标测试集 310 项基础回归 + 4 项对象解析测试全部通过。
- 尚未宣称 P4 完成：物流、报价、库存、付款账户连接器和领域结果自动验收仍需接入实际业务系统；当前付款账户没有默认来源，不会把 iLink 登录账户当作付款账户。

## 3. 目标对象关系

```text
WorkRequest（用户自然语言请求）
  └─ TaskThread（Channel 多轮上下文）
       └─ TaskInstance / WorkItem（正式可执行任务）
            ├─ TaskTemplateVersion（可选的流程蓝图）
            ├─ DataContextSnapshot（本次使用的数据和版本）
            ├─ ExecutionAttempt（执行、重试、恢复）
            ├─ TaskRevision（用户反馈后的修订）
            ├─ AcceptanceCheck（验收项及结果）
            └─ EvidenceRecord（数据、操作、输出和验证证据）
```

### 3.1 对象职责

| 对象 | 职责 | 是否进入执行队列 |
| --- | --- | --- |
| WorkRequest | 保存用户原始表达和附件入口 | 否 |
| TaskThread | 管理 Channel 多轮上下文和当前任务 | 否，作为上下文容器 |
| TaskTemplateVersion | 定义输入、步骤、风险、输出和验收规则 | 否 |
| DataContextSnapshot | 固化本次任务实际使用的数据 | 随任务进入 |
| WorkItem | 一次正式、可追踪的工作 | 是 |
| ExecutionAttempt | 一次实际执行或重试 | 是 |
| TaskRevision | 对目标、数据、规则或输出的修订 | 触发重新执行时进入 |
| EvidenceRecord | 证明任务依据、动作和结果 | 否，随生命周期产生 |

模板不是用户必须选择的表单。重复稳定的工作使用模板；临时探索性工作使用通用任务。模板只保存规则和结构，不保存本次任务的真实数据、凭证或敏感结果。

## 4. 普通用户目标体验

### 4.1 首次请求

用户：

> 帮我把这几份报价整理一下，给客户一份好看的版本。

系统：

> 我先按你之前给客户的格式整理。已找到 3 份报价资料，但其中 1 份没有客户名称。可以先整理草稿，客户名称暂时留空吗？

用户只需回复“可以”。系统后台完成模板匹配、资料记录、验收标准生成和任务创建。

### 4.2 结果修订

用户：

> 这个不对，客户不是这个，按上个月那份报价来。

系统：

> 明白，我改用上个月该客户的报价记录重新整理。原版本会保留，新的版本完成后发你对比。

系统应自动识别为：修正数据来源，而不是创建无关的新任务。

### 4.3 专业复盘

用户：

> 查看依据。

微信端只返回摘要：

> 本次使用了上个月客户报价和当前产品资料。详细过程已整理到桌面端任务复盘。

桌面端展示完整证据链；用户不需要每次都进入专业视角。

## 5. 详细开发阶段

## P0：统一任务合同和迁移策略

### 目标

为 Channel、桌面端、Work Item 和 AutoRun 建立同一套可持久化任务合同。

### 开发项

1. 增加任务合同字段：
   - `request`：原始请求摘要和来源事件；
   - `goal`：系统归一化后的目标；
   - `domain`：办公、开发、内容或通用；
   - `templateBinding`：模板 ID、版本、匹配理由、置信度；
   - `dataContext`：数据快照引用；
   - `riskProfile`：风险级别、风险信号、确认要求；
   - `acceptanceCriteria`：验收标准；
   - `verificationSop`：验证步骤；
   - `outputContract`：预期结果和输出格式；
   - `revision` / `revisionHistory`：修订版本；
   - `evidenceRefs`：证据引用。
2. 为旧 Work Item 提供兼容默认值，不强制一次性迁移历史任务。
3. 区分“草稿合同”和“已确认执行合同”。
4. 将合同摘要写入 AutoRun/Invocation 的只读执行快照。
5. 为敏感字段做本地持久化和公共视图脱敏。

### 预计涉及

- `apps/server/src/services/work-items.mjs`
- `apps/server/src/services/channel-conversation.mjs`
- `apps/server/src/services/auto-run.mjs`
- `apps/server/src/runtime/service-composer.mjs`
- `packages/protocol/src/`
- 持久化 schema 和状态迁移

### 验收

- 新旧 Work Item 都能被读取。
- Channel 任务和桌面任务使用同一份合同。
- 合同确认后不可被无版本地覆盖。
- AutoRun 执行时使用的是冻结快照，而不是执行中不断变化的草稿。

## P1：Channel 接入模板匹配和验收合同

### 目标

让微信任务自动匹配模板或回退到通用任务，用户不需要知道模板存在。

### 开发项

1. Channel 任务创建前调用现有模板匹配能力。
2. 匹配结果写入任务草稿：模板、版本、理由、置信度、缺失字段。
3. 复用 `suggestWorkItemDraft` 的验收标准和验证 SOP 生成逻辑。
4. Channel 任务创建时传入：
   - `acceptanceCriteria`
   - `verificationSop`
   - `executionContractSource`
   - `myTemplateBinding`
5. 低置信度模板匹配不自动套用，使用通用任务并在桌面端标记待复核。
6. 微信确认消息只展示业务摘要，不展示模板 ID。

### 验收

- “整理报价”“跟踪订单”“修复登录问题”“改写文章”等请求可以分别匹配或合理回退。
- 用户无需输入模板名称。
- 任务详情可以看到使用的模板版本和验收标准。
- 模板匹配错误不会污染原始任务；可以改用通用任务或重新匹配。

## P2：数据上下文和来源快照

### 目标

让系统能够说明“这次任务使用了什么依据”。

### 开发项

1. 统一 `DataContextSnapshot` 结构：
   - 来源类型和来源 ID；
   - 文件路径或外部记录引用；
   - 读取时间；
   - 版本、哈希或更新时间；
   - 读取范围；
   - 可信度和状态；
   - 是否经过用户确认。
2. 先接入现有来源：
   - Channel 输入附件；
   - 本地项目文件；
   - 代码仓库和工作树；
   - 历史 Task Thread 和 Work Item；
   - 任务输出资产。
3. 增加只读数据上下文解析器，先查找和摘要，不直接修改外部数据。
4. 为外部连接器预留统一接口：客户、订单、物流、报价、库存、财务。
5. 数据来源失效或版本变化时，让任务进入“需要重新确认”，不能静默使用旧数据。

### 验收

- 任务详情可以列出所有实际使用的数据。
- 数据文件被替换后，系统能够发现哈希或版本变化。
- 用户可以看到“使用了哪一份资料”，但看不到不必要的内部路径和凭证。
- 没有数据依据时，系统明确标记为通用建议，而不是伪装成事实。

## P3：风险路由和确认体验

### 目标

让低风险工作足够顺畅，高风险动作可控。

### 风险级别

- `low`：咨询、总结、分类、分析。
- `local_change`：修改本地代码、文档、图片或视频。
- `external_communication`：发送邮件、报价、发货通知、发布内容。
- `financial`：汇款、付款、财务数据变更。
- `destructive`：删除、覆盖、批量修改。

### 开发项

1. 模板和能力声明风险级别。
2. Channel 根据目标、工具和数据推断风险，但高风险必须由确定性规则兜底。
3. 低风险任务可以直接执行或只需简单确认。
4. 对外发送前展示对象、内容、附件和影响。
5. 资金、删除和批量修改必须二次确认，并记录确认内容。
6. 确认内容与任务合同绑定；任务目标、数据或收款对象变化后，旧确认自动失效。

### P3 首批实现边界（已落地）

- `low` / `local_change` 保持个人 Channel 的原有确认后排队路径。
- `external_communication`、`financial`、`destructive` 在个人 Channel 中先保存为 `backlog` Work Item，并建立待路由请求。
- Channel 回复“确认执行”调用与桌面端相同的 `routeChannelTask`；不会重新创建任务，也不会创建第二个执行队列。
- Channel 回复“取消”会关闭待路由请求并结束线程；重复确认只返回已排队提示，不重复路由。
- 团队 Channel 仍遵循管理员审批路径；个人 Channel 的确认只代表本人对本机任务的二次确认。
- 当前风险信号是确定性文本兜底，尚未绑定实际收件人、最终附件、金额和能力调用参数；因此 P3 后续必须增加“执行前预览 + 合同摘要哈希 + 目标对象校验”。
- P3.2 已完成“执行前预览 + 预览摘要绑定 + 变化失效”；当前对象仍是自然语言推断值，尚未接入真实联系人、订单、账户或发布平台的强校验。
- P3.3 已完成本地确定性必填校验；真实联系人、订单、账户和发布平台仍需连接器提供可验证对象后才能放行。

### 验收

- “整理报价草稿”不需要复杂审批。
- “发送报价”必须展示收件人和最终文件。
- “汇款”不能因为用户一句“帮我汇款”直接执行。
- 任何高风险动作都有可追溯的确认和拒绝记录。

## P4：真实对象校验、结果验证和完成门禁

### 目标

不能把“Bridge 返回成功”直接等同于“业务任务完成”，也不能把自然语言中的对象名称直接当成真实联系人、账户或发布目标。

### 开发项

1. 在执行前解析并校验真实对象：
   - 联系人/客户、订单：本机业务实体或连接器同步记录；
   - 账户：仅接受明确登记且脱敏可展示的付款账户；
   - 文件：本机工作流制品或 Channel 附件的当前指纹；
   - 发布平台：已启用 Channel 或连接器登记的发布目标。
2. 将验收标准分为：
   - 文件/格式验收；
   - 数据一致性验收；
   - 业务规则验收；
   - 执行结果验收；
   - 用户确认验收。
3. 复用现有 `completionGate`、`verificationRecords` 和 `reviewEvidence`。
4. 为每个领域增加最小验证器接口：
   - 开发：测试、类型检查、变更范围；
   - 办公：字段完整、金额一致、版本有效；
   - 内容：格式、长度、媒体可读性、输出数量。
5. 对象失效或验收失败时进入 `needs_attention` 或 `waiting_user`，而不是标记成功。
6. 结果消息展示“完成内容 + 验证结果 + 未通过项”。

### 验收

- 每个正式任务都有验收标准，或明确记录“通用任务、无自动验收”。
- 验收记录关联到当前输出版本和执行尝试。
- 验收失败可重新执行，不覆盖之前结果。
- 微信端能用一句话说明失败原因和下一步。

## P5：Task Revision 和自然返工

### 目标

支持用户不懂内部流程也能反复调整，并保证历史版本可复盘。

### 开发项

1. 增加修订类型：
   - `data_correction`：数据来源或数据值错误；
   - `interpretation_correction`：理解目标错误；
   - `template_correction`：流程或规则错误；
   - `execution_correction`：执行动作错误；
   - `output_style_correction`：格式、语气、风格错误；
   - `acceptance_correction`：验收标准不完整。
2. 支持自然语言反馈：
   - “这个不对”；
   - “客户弄错了”；
   - “按上个月那份”；
   - “只改价格”；
   - “格式保持不变”；
   - “重新检查一遍”。
3. 系统无法判断时只追问一项：
   > 是数据不对、理解不对，还是格式不对？
4. 每次返工创建新的 `TaskRevision`，保留旧版本、差异和原因。
5. 仅在用户明确确认时，把本次修正沉淀到 My Template。

### 验收

- 用户说“再改一下”不会被误判为完全无关的新任务。
- 旧版本仍可查看和重新发送。
- 新版本可以比较输入、规则、输出和验收差异。
- 一次任务的修正不会未经确认影响所有未来任务。

## P6：Channel 专业复盘和按需专家指导

### 目标

普通视角保持简单，专业视角能够深挖问题。

### 开发项

1. 新增 Channel Task Review read model，统一聚合：
   - ChannelEvent；
   - TaskThread；
   - WorkItem；
   - AutoRun/Invocation；
   - Delivery；
   - DataContextSnapshot；
   - TaskRevision；
   - AcceptanceCheck；
   - EvidenceRecord。
2. 桌面端增加“任务复盘”入口和时间线。
3. 提供四个重点问题视图：
   - 我当时说了什么？
   - 系统理解成什么？
   - 使用了哪些依据？
   - 错误发生在哪一步？
4. 微信端支持低频指令：
   - “查看依据”；
   - “为什么这样做”；
   - “深入分析”；
   - “哪里出错了”；
   - “只修正这次”；
   - “以后按这个规则”。
5. “深入分析”调用 Bridge 时必须是受限的分析任务，默认只读，不直接修改模板或业务数据。

### 验收

- 普通用户不用打开桌面端也能完成日常任务。
- 需要复盘时，桌面端能从一条时间线看到完整过程。
- 专家指导默认低频触发，不阻塞普通任务。
- 指导结果可以选择只修正当前任务，或申请升级模板。

## P7：业务试点和外部数据连接

### 目标

验证“数据驱动”不是只停留在本地文件和开发任务。

### 推荐试点顺序

1. 开发：根据 Issue、代码和测试结果修复问题。
2. 办公：订单/物流查询、报价草稿。
3. 内容：文章整理、图片处理、视频素材整理。
4. 对外发送：报价邮件、发货通知、内容发布，全部采用预览确认。
5. 财务：最后再做汇款相关流程，并要求强校验和二次确认。

### 试点验收

- 每个试点至少有一个模板版本。
- 每个模板至少有三组真实或脱敏数据案例。
- 每个案例有输入、执行、验收和失败复盘记录。
- 至少覆盖一次数据错误、模板错误、执行错误和用户修改。

## 6. 测试计划

### 单元测试

- 任务合同默认值和状态迁移。
- 模板匹配、低置信度回退和版本绑定。
- 数据快照哈希、版本漂移和来源脱敏。
- 风险分类和确认失效。
- 个人 Channel 高风险任务先停留在待确认，确认后只路由一次，取消和重复确认可回归。
- 修订类型识别、版本生成和差异记录。
- 验收门禁和验证结果关联。

### Channel 集成测试

- 普通用户只发送自然语言，不发送任务 ID。
- 多条补充消息合并成一个任务。
- “另外”创建新任务，“再改一下”修改当前任务。
- 多任务排队时，结果乱序仍能正确关联。
- 任务执行中补充图片、语音、文件。
- 数据版本变化后要求重新确认。
- 高风险操作预览、确认、拒绝和确认失效。
- 任务失败、重试、重启恢复和人工接管。
- 结果生成但微信投递失败时可重发。

### 专业复盘测试

- 能从 Channel 消息跳到统一任务复盘。
- 能查看模板版本、数据来源、执行尝试和验收证据。
- 能比较两个任务修订版本。
- 删除或脱敏敏感数据后，复盘仍保持引用完整性。
- 专家指导不会直接绕过原有审批和能力网关。

### 用户验收测试

使用普通用户语言，不允许测试者使用内部术语：

- “帮我整理这个”；
- “按上次方式做”；
- “这个不对”；
- “再改一下”；
- “先别发”；
- “为什么这么做”；
- “帮我看看哪里错了”。

验收重点不是模型是否猜中所有内容，而是：猜不中时是否能安全、简洁地追问，并且不会丢失上下文或产生不可逆动作。

## 7. 发布门禁

满足以下条件后，才进入真实办公数据试点：

- Channel 任务全部绑定任务合同。
- Channel 任务至少有输入来源、执行记录和输出来源。
- 高风险操作有确定性确认门禁。
- 任务结果不再只依赖 Bridge 成功状态。
- 修订不会覆盖历史结果。
- 桌面端能够查看失败原因和证据。
- 任务模板升级不会影响历史任务。
- 外部连接器权限和数据范围可以撤销。
- 关键路径有重启恢复和重复消息测试。

## 8. 暂不做的内容

- 不要求用户手动选择办公、开发或内容模板。
- 不把所有自然语言都强制转成复杂表单。
- 不为咨询单独建立一套脱离任务治理的执行体系。
- 不默认自动修改未来模板。
- 不在没有数据来源和验收标准时宣称企业级可靠。
- 不把汇款、批量发货、正式发布作为第一批全自动能力。

## 9. 推荐当前开工顺序

```text
P0 统一任务合同
  ↓
P1 Channel 接入模板和验收
  ↓
P2 数据上下文和来源快照
  ↓
P3 风险路由和确认
  ↓
P4 结果验证和完成门禁
  ↓
P5 Task Revision 自然返工
  ↓
P6 专业复盘和专家指导
  ↓
P7 业务数据连接与试点
```

优先完成 P0～P2，再扩大办公和自媒体能力。否则会出现“意图识别越来越聪明，但结果仍无法说明依据和正确性”的问题。

## P4.2 CSV/Excel/JSON 导入与业务连接器同步

P4.2 的目标是让普通用户可以把已有业务资料接入 Channel 对象校验，同时保留专业可追溯性：

- 支持 CSV、JSON、XLSX/XLS（首个工作表）导入；文件先在本机读取并转成受控预览，服务端不保存原始文件。
- 导入必须经过“预览 → 校验 → 确认”三步；缺少名称、重复业务标识、格式错误或超限时禁止确认。
- 账号只保留后四位；导入记录只保留脱敏后的预览、错误行、文件摘要和确认结果。
- 导入确认具有幂等性，重复点击不会重复创建对象；导入记录和业务对象均按团队、项目隔离。
- 首个真实连接器为本地 `business_entities`，把已有联系人/订单实体只读同步到 Channel 对象登记表。
- 外部业务系统使用只读 `list()` 适配器接入；同步过程不执行外部写操作，未配置适配器时明确返回未配置/失败，不伪造同步成功。
- 同步和导入都写入审计事件，后续可在任务复盘中追踪来源、导入批次、对象版本和确认时间。

下一步是把外部适配器配置、凭据健康检查和同步结果展示接入设置页，再以联系人、订单两个低风险对象做真实数据试点；账户、发货、汇款和正式发布仍需额外的高风险确认门禁。

## P4.3 本地业务文件闭环

P4.3 先围绕普通用户已有的 CSV、Excel、JSON 文件跑通完整业务链路，不要求绑定 CRM、ERP 或订单平台：

- 用户选择联系人或订单文件，系统在本机读取并展示预览、错误行和可导入数量。
- 文件读取通过统一的 `local_file` 只读源适配器进入标准化行记录；适配器只负责读取和字段标准化，不直接写任务或业务对象。
- 用户确认后，文件数据进入团队/项目范围内的业务对象登记表；服务端只保留脱敏摘要、文件哈希、导入批次和对象版本，不保存原文件。
- Channel 任务从导入对象中匹配“发给张三”“跟踪订单 ORD-001”等自然语言目标，并在确认快照中记录对象来源和版本。
- 同一业务对象再次导入会更新版本；如果任务确认后对象版本发生变化，任务重新要求确认，避免使用过期联系人或订单信息。
- 导入、对象更新、确认、版本失效和失败重试均保留审计记录；重复确认和重复导入不会造成不可控重复数据。
- `business_entities` 只读同步和外部连接器协议保留为后续扩展，不作为当前普通用户跑通业务的前置条件。

P4.3 验收以“本地联系人 CSV → 导入确认 → Channel 识别联系人 → 任务确认 → 对象版本变化后重新确认”为最小闭环，再扩展订单 Excel 和多文件合并。

## P4.5 模板数据需求与运行时数据计划

模板负责声明“完成这类工作需要哪些抽象数据”，任务运行时才把它绑定到具体的本地文件版本：

- `dataRequirements` 只描述数据类型、用途和必要字段，例如“客户表需要 name、email”；不允许写入具体路径、原始内容或凭据。
- `relations` 只描述需求之间的关联字段，例如订单.customer → 客户.name；它是可追溯的关联计划，不代表执行器会暗中合并文件。
- Channel 创建任务时生成 `dataPlan`，记录匹配到的本地文件、文件摘要、行数和 revision；没有来源或来源不唯一时明确停在“需要数据/需要选择来源”。
- 数据计划进入任务合同并冻结；执行前重新检查文件 revision、哈希和来源状态，变化后原确认失效，要求按最新文件重新预览。
- 普通用户只看到“还需要客户表”或“使用客户表.xlsx（第 3 版）”，专业复盘可查看需求、来源、关联状态和摘要版本。

这一层把模板边界和任务执行边界分开：模板定义数据需求，Channel 负责理解并生成计划，任务执行器只消费已确认的数据计划；实际多文件关联执行作为后续 P4.6，在验证字段和关联结果后再开放。

## P4.6 只读多文件关联预览

P4.6 首先只做可解释、可复核的关联预览，不直接写回源文件或业务对象：

- 按已冻结 `dataPlan` 的来源和关联字段读取已登记对象。
- 只输出匹配数、未匹配数、字段缺失、重复关联和对象 revision 摘要，不把原始账号、凭据或整行内容写入任务合同。
- 关联字段缺失、关键记录未匹配或对象 revision 变化时，任务停在“需要复核”，不会自动猜测或继续执行。
- 关联预览摘要和对象 revision 进入任务合同；确认前再次计算，关联结果变化会使原确认失效。
- Channel 用普通语言提示“数据文件已找到，但关联结果还需要确认”，任务详情页展示关联计划和匹配统计，专业人员可追溯具体失败原因。

当前不开放自动合并写回、多对多业务决策和高风险外部动作；这些需要在真实数据样本上确认业务规则后单独验收。

## P4.7 关联结果独立验证记录

P4.7 把“系统算出了可用关联”“用户确认了这次关联”和“任务最终输出”明确分开，避免一次预览被误当成永久事实：

- 每次可执行的关联结果生成独立的 `channelDataRelationConfirmations` 记录，保存任务、Channel、数据计划摘要、关联摘要、对象 id/revision 快照、验证时间和验证方式。
- 自动放行的低风险任务记录 `runtime_verified`；需要用户确认的任务在确认边界记录 `user_confirmation`，两者都绑定到任务合同，桌面端显示“已验证并留痕”。
- 记录只保留对象引用和 revision，不保存关联字段的原始值；任务详情和事件时间线可以说明验证依据，但不会把业务敏感内容扩散到审计摘要。
- 执行前仍重新校验数据计划和关联预览；文件或对象版本变化时拒绝旧确认，历史验证记录保留为当时事实，不覆盖成最新结果。
- 状态集合、持久化、租户隔离、自检重置、Channel 会话同步和 Web 详情展示均有覆盖，重启后可以继续区分系统校验与用户复核。

P4.7 的边界仍然是“可验证关联”，不是自动替用户作业务判断；多对多解释、异常匹配处理和高风险外部动作需要真实样本验收后再单独开放。

## P4.8 多文件、多记录、多字段变更安全门禁

本阶段审核发现：现有能力可以批量导入多个 CSV/Excel 并更新对象登记表，但不能把自然语言中的“修改表格”直接当成安全的文件写回计划。已补上以下门禁：

- 检测到“修改/更新/删除/新增/回填”等写操作，同时目标涉及 CSV、Excel、工作簿或数据表时，生成 `dataMutationPreview`，记录候选文件、文件 revision、哈希和行数。
- 任务模板可以声明 `mutationPolicy`：允许的操作、目标数据需求、主键字段、可修改字段、是否允许多文件/多记录、最大记录数和安全写入模式；模板只定义边界，不绑定具体文件路径。
- 任务运行时把模板边界绑定到本次实际文件和 revision；模板不允许多文件或多记录时，任务直接停在模板边界阻断，不由意图识别器自行放宽权限。
- 多文件任务保留所有候选来源；用户没有明确提到文件名时，不自动猜测目标文件。记录范围、字段和值、是否修改全部匹配记录仍是必填项。
- 任务合同可以进一步绑定 `dataMutationScope`：每个目标文件必须带当前 revision/哈希、记录定位摘要（只存 digest、匹配条数，不存原始筛选值）、预计影响条数和字段变更摘要（只存字段、操作和值摘要，不存原始新值）。服务端会再次按 `mutationPolicy` 校验主键字段、可修改字段、多文件/多记录权限和最大条数。
- `rowSelector`、`fieldChanges`、`estimatedAffectedRows` 在没有结构化计划前保持空值；有计划时只能生成 `ready` 范围预览，但 `writeMode` 仍固定为 `not_authorized`。这意味着当前阶段只做变更范围复核，不执行文件写回。
- 任何待复核的文件变更任务都不会自动进入 Bridge/AutoRun 队列；执行前还会重新比较所有目标文件 revision 和哈希，文件变化后原预览失效。
- 普通用户会看到候选文件和需要补充的三类信息；专业复盘可以看到任务合同中的候选源、版本、摘要和阻断原因。

下一阶段如要真正支持写回，应新增“安全副本 → 变更 diff → 用户确认 → 原子替换/失败回滚 → 输出文件校验”的执行器，并按文件、记录、字段粒度写入审计证据；在该执行器完成前，即使任务范围已经完整，路由层也会明确拒绝写回，Bridge 不得凭自然语言直接修改源 CSV/Excel。

## P4.11 可扩展批量写回与源文件身份校验

P4.11 在不削弱 P4.8/P4.10 安全门禁的前提下，把“多记录、多字段、多文件”落到可追踪的批次模型：

- 单条 Ledger 预览继续负责一条业务记录的字段 diff；同一条记录可以一次修改多个字段。
- 新增批次预览，包含多个子预览和目标文件数量；一次用户确认可以按文件队列顺序提交多条记录，子项仍使用既有版本检查、文件锁和原子替换。
- 批次支持显式文件范围；Channel 的多句请求必须用文件名分隔，例如“把 customers.csv 里的 1001 的客户改成 A；把 orders.csv 里的 1001 的状态改成已发货”。缺少文件范围、重复记录字段目标或包含删除/全部/模糊批量语义时直接阻断。
- 批次不是跨文件瞬时事务。文件系统无法保证多个文件同时替换，因此持久化 `ledgerBatchMutationJournals`，记录已完成子项、失败子项和 partial 状态；重启或重试不得伪造“全部完成”，用户能看到剩余范围并继续处理。
- Channel 绑定除了项目、文件名、格式和 revision 外，还必须比较导入文件快照与当前 Ledger 目标文件的原始字节 SHA-256。身份不一致时要求重新导入或重新绑定，不能只依赖文件名或语义 revision。
- 新增目标文件身份只读接口，返回路径范围内的大小、mtime、原始内容哈希和语义 revision；不返回文件内容。写回审计继续保存 before/after hash、字段列表、来源证据和批次引用。
- 批次创建、提交、队列等待、部分失败和幂等重放均按 owner/project 隔离；单个子预览不能绕过批次直接提交。

P4.11 的普通用户交互保持“说明要改什么 → 展示影响几条/几个文件 → 回复确认执行”，专业用户可以在任务详情查看每个文件、记录、字段的 diff 和身份哈希。跨文件补偿回滚、Excel 复杂结构的全量保真恢复和大规模异步批次继续作为 P4.12，在真实样本验收后开放。

### P4.11.1 Channel 批次入口

Channel 已接入显式分句批次：每个分句必须包含目标文件名，系统按文件绑定 Ledger 定义，再生成统一批次预览；没有文件范围、重复字段目标或模板未允许多记录/多文件时阻断。单条请求继续沿用 P4.10 路径，批次请求使用批次提交接口，避免用户接触内部预览 ID。

## P4.12 批次失败补偿、重试恢复和跨文件审计增强

P4.12 将 P4.11 的“多文件批次可执行”提升为“失败可解释、可补偿、可恢复”。这里不宣称跨文件系统事务；本地 CSV/Excel 仍是多个独立文件，系统通过批次 journal 和提交前快照，把可安全恢复的边界显式化。

### P4.12.1 安全提交与补偿

- 批次开始提交前，为每个唯一目标文件创建本地受保护的回滚快照；快照保存原始内容哈希、语义版本、文件权限和批次关联，不把原始文件内容写入业务状态或 HTTP 响应。
- 每个子操作成功后，journal 持久化 `appliedPreviewIds`；重启或进程中断后，已写入的子操作会被识别并跳过，不重复追加或修改记录。
- 某个子操作失败时，只在当前目标文件仍匹配批次预期结果的情况下恢复快照；如果用户、外部程序或其他进程已经修改文件，则停止补偿并标记 `needs_attention`，不覆盖新内容。
- 全部恢复成功时，已写入的子预览标记为 `rolled_back`，批次标记为 `rolled_back`，回滚快照清理状态同时进入审计；外部漂移时保留 journal 供人工处理。

### P4.12.2 重试与重启恢复

普通用户不需要理解 journal 或预览 ID：桌面端/Channel 只需显示“正在恢复”“已回退”“需要检查文件”并提供“重试”或“查看详情”。专业入口增加：

- `POST /api/workflow-memory/ledger-batch-upsert-previews/:id/retry`：继续 `committing/partial` 批次；已完成子操作幂等跳过。
- `GET /api/workflow-memory/ledger-batch-mutation-journals`：按批次或状态查看恢复、失败和补偿记录。
- `rolled_back` 批次不允许直接重试，要求重新生成预览；`needs_attention` 批次必须先处理外部文件漂移再人工恢复，避免自动覆盖。

### P4.12.3 跨文件审计字段

批次审计统一记录批次、子预览、已应用子操作、失败子操作、每个目标文件的前置版本、快照恢复结果、阻断原因、清理状态和时间线。对普通用户只展示文件数量、影响记录数、当前阶段和下一步；原始路径和回滚快照路径不通过公开接口泄露。

P4.12 的验收重点：正常失败能够恢复到批次前状态；恢复期间发生外部修改能够阻断而不是覆盖；中断重启后不重复写入；跨文件结果可按一个批次追溯。Excel 复杂结构的长期保真、超大文件异步快照和真正跨存储事务不在本阶段承诺范围。

## P4.13 安全和数据保护

P4.13 以“本机数据也不能因为日志、快照或错误响应而意外扩散”为原则，补齐数据写回链路的最小权限、脱敏和残留治理。

### P4.13.1 本地文件与状态保护

- 批次回滚快照使用 `0600` 权限，不继承源文件的可读权限；恢复临时文件和已知残留只按当前批次、已授权目标文件的精确路径清理。
- JSON 状态快照使用原子写入并统一收紧为 `0600`，覆盖任务上下文、批次 journal、数据源版本等本地受治理信息。
- 快照不把原始文件内容写入状态或 API 响应，只保留内部恢复所需的本地路径、哈希、权限和状态；公开审计隐藏回滚文件路径。
- 发生外部文件漂移、快照路径异常或清理失败时，进入人工处理状态，不自动删除或覆盖未知文件。

### P4.13.2 数据最小化与响应脱敏

- Ledger 公开 diff 对账户、银行卡、密钥、凭证、token、密码等敏感字段只显示 `[redacted]`；内部执行仍保留必要值，且只在本地受治理写回链路中使用。
- 批次预览失败不再回传完整原始操作对象；错误响应仅返回错误码、失败序号和有限的版本/缺失字段信息。
- 跨文件审计只返回恢复计数、状态、哈希和阻断原因，不返回原始路径、快照路径或文件内容。
- 业务键、字段名称和任务摘要继续按用途保留，但不把凭证、原始提示词和原始文件内容带入 Channel 消息或审计摘要。

### P4.13.3 验收边界

P4.13 验收覆盖：跨团队读取/提交仍被拒绝；敏感 diff 不泄露值；回滚快照和状态文件为私有权限；补偿完成后快照不残留；错误响应不包含原始操作内容。操作系统磁盘加密、企业密钥托管和多用户共享机器的完整安全域仍属于部署层要求，不由本阶段伪装成应用层能力。
