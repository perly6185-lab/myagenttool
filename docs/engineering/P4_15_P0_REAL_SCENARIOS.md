# P4.15 P0 真实业务场景验收

## 目标

用普通用户能理解的业务语言，验证 iLink → 意图 → 数据计划 → 任务 → 预览/确认 → 本地文件处理 → 结果回复 → 审计追溯的完整链路。

## 执行

```bash
pnpm test:p0:real-scenarios
pnpm test:p0:real-excel
```

报告写入：`.myagenttool/real-scenarios/p0-report.json`。

## P0 场景

| 场景 | 当前验收 | 数据与风险边界 |
| --- | --- | --- |
| 客户报价跟踪 | `quotations.csv` 定位报价单、预览跟进状态、确认后写回、审计 | 仅修改明确编号和明确字段 |
| 订单发货异常 | `orders.csv` + `shipments.csv` 批次预览、多个字段写回、结果交付 | 所有文件、记录和字段必须在预览中明确列出 |
| 汇款对账（只读核对） | Channel 自然语言触发本地应收与银行流水对象匹配，返回未匹配和差异报告 | 只读，不自动修改原始文件；差异处理另起变更任务 |
| 报价到回款、售后、完结全流程 | 在报价、订单、发货、回款同步、售后和完结等不同时间节点持续推进同一客户事项，并保留多文件审计 | 每次写回仍需明确预览和确认；回款对账只读；外部改动使旧预览失效 |
| 微信普通用户多轮操作 | 文本、图片、语音、文件、补充消息、确认、长任务结果和任务关联 | 不要求用户知道任务 ID 或运行 ID |

## 每个场景的验收点

1. 用户只描述业务目标，不提供内部 ID。
2. 系统能说明理解结果和使用的数据文件。
3. 数据不足时只追问必要信息。
4. 任何写回都先给出文件、记录、字段和预计影响数量。
5. 用户未确认时，原始文件不得变化。
6. 确认后回复业务结果，不暴露内部任务 ID、Trace 或路径细节。
7. UI 和审计记录可以追溯原始输入、数据来源、预览、确认和最终变更。

## 后续增强

- 已将对象级只读匹配接入本地 CSV/Excel 导入后的 Channel 数据计划。
- 已支持应收账款与银行流水按业务单号、金额、日期容差的可解释匹配。
- 已通过普通用户回复返回差异清单，并保留来源文件和结果摘要审计。
- 对账差异的人工确认后批量回写仍保持为独立的后续变更任务，避免把只读核对误变成财务写操作。
- 报价到完结全流程已覆盖不同时间节点、报价/订单/发货/售后多文件写回、延迟回款数据导入和版本漂移后重新导入恢复。
- 回款到账确认已拆成独立的“回款确认”写回任务：对账只读，确认到账后仍需单独预览和确认，避免把匹配结果误当成财务入账。
- 本地对象导入已保留订单、发货、回款和售后状态，并在 Channel 页面提供按客户/订单聚合的业务链快照；快照明确标注最近导入来源，不伪装成实时数据库。
- 业务链已按“订单主链 + 环节记录集合”建模：报价、发货、应收/到账、售后和退货都保留多条记录，并提供金额、数量汇总；同一客户存在多个订单且记录缺少订单号时会标记待确认，不会猜测归属。
- 本地连接器新增退货对象和字段：退货单号、订单号、退货状态、退货金额、退货数量、退货原因。
- Ledger 模板可声明状态流转边界，例如“已发货 → 已完成”；不允许的跨阶段跳转在预览前拒绝。模板只声明通用边界，实际订单号、文件和字段仍由当前任务绑定。
- 对不存在的现有记录，模板禁止插入时会明确提示“先导入或建立这条业务记录”，不会静默创建新订单。
- `pnpm test:p0:real-excel` 已使用落盘后的真实 XLSX 工作簿，重新读取后完成报价、订单、分批发货、分批回款、到账流水、多笔售后和退货导入，并校验主链汇总。
- Excel 导入按环节优先使用报价单号、发货单号、售后单号、退货单号、应收/回款单号和银行流水号；缺少环节主键时使用可解释的组合字段或受控行号兜底，避免同一订单覆盖多条历史记录。

P0 场景脚本只编排已有受治理的测试旅程，不复制生产逻辑；若某场景能力尚未实现，报告必须保留明确限制，不能以“测试通过”替代产品能力。
