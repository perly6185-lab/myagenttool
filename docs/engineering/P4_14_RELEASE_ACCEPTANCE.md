# P4.14 审核、验收与发布门禁

更新时间：2026-08-17

P4.14 的目标是把 P4.10–P4.13 从“代码已实现”提升为“有证据、可发布、可回滚”。发布门禁不以单个测试通过作为结论，而以代码、数据、安全、构建和用户流程共同通过为准。

## 1. 验收范围

| 能力 | 发布要求 | 证据 |
| --- | --- | --- |
| P4.10 单记录写回 | 预览、确认、版本校验、原子写回、审计通过 | Ledger 单记录测试、Channel journey |
| P4.11 多记录/多文件 | 显式文件范围、字段 diff、批次确认、租户隔离 | 批次 Ledger 测试 |
| P4.12 补偿恢复 | 失败补偿、外部漂移阻断、重启续作、幂等重试 | 批次故障注入测试 |
| P4.13 数据保护 | 敏感 diff 脱敏、快照/状态 `0600`、快照清理、错误最小化 | P4.13 security test |
| Channel 普通用户流程 | 不要求用户知道内部 ID；确认、失败、回退、人工处理提示可理解 | Channel conversation/integration tests |
| Web 控制台 | 类型检查、生产构建、批次状态可显示 | Web typecheck/build |
| 发布产物 | 当前平台构建产物可验证；Windows/Linux 必须在原生 runner 验证 | desktop preflight/package verify |

## 2. 执行门禁

本机发布前执行：

```text
pnpm release:p4-14:check
pnpm release:p4-14
```

`release:p4-14` 会生成：

```text
.myagenttool/release-candidate/p4-14-<platform>-<arch>.json
```

该 manifest 记录检查项、版本、平台、耗时和有限的尾部输出，不记录文件原文、凭证或完整任务内容。发布候选还必须执行：

```text
pnpm test:ci
pnpm ci:simulate --job verify
pnpm release:candidate
```

CI 需要在 Linux、macOS、Windows 原生 runner 分别生成候选证据。跨平台构建不能用 macOS 上的静态推断替代 Windows/Linux 原生构建。

## 3. 人工验收

发布前至少走一遍以下真实用户路径：

1. 发送普通咨询，确认不会误创建写回任务。
2. 发送单文件单记录修改，确认预览、确认、写回和审计完整。
3. 发送明确列出两个文件的批量修改，确认系统显示文件数、记录数和字段范围。
4. 在批次中途制造第二文件失败，确认已完成文件自动回退。
5. 在补偿前修改目标文件，确认系统停止补偿且不覆盖新内容。
6. 重启桌面端后继续中断批次，确认不会重复写入。
7. 检查普通用户消息不出现内部路径、快照路径、原始敏感字段值或强制任务 ID。

## 4. 发布阻断条件

任一条件成立即不发布：

- 任何 P0/P1 安全问题、跨团队读取、越权写回或敏感数据泄露。
- 批次失败后出现部分写入但无 journal、无补偿结果或无法人工定位。
- 外部文件发生变化后仍自动覆盖文件。
- 任一平台缺少原生构建或候选证据 manifest。
- Server/Web 类型检查、生产构建、CI gate 或 P4.14 gate 失败。
- 发布说明缺少已知限制、数据影响或回滚说明。

## 5. 回滚与发布结论

P4.14 只负责形成发布候选和证据，不自动打 tag、上传安装包或发布生产环境。发布需要人工确认：

- 回滚到上一候选版本不会破坏已有状态快照；
- P4.12 journal 能被当前版本读取；
- 新版本写入失败时，用户可以看到“已回退”或“需要检查”，而不是成功假象；
- 生产发布、安装包分发和 GitHub Release 均经过明确批准。

最终结论只能使用以下状态之一：`passed`、`passed_with_known_limitations`、`blocked`。未提供平台证据时不得标记为 `passed`。
