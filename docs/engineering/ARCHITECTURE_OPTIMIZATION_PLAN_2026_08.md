# 架构优化计划（2026-08）

## 目标

在不改变普通用户任务流程的前提下，把当前“功能可用但修改半径过大”的结构，逐步调整为可替换、可验证、可独立演进的模块边界。优先治理任务执行与持久化，因为它们同时影响稳定性、风险复核、开发动作和办公批次动作。

本计划采用小批次迁移：每一批都必须保持现有 API、状态语义和用户界面行为，并可独立回滚。

## 2026-08-28 基线

当前主要热点按本批改造开始前的源码行数统计如下。行数不是质量结论，但能反映职责聚集和变更冲突风险。

| 模块 | 行数 | 当前聚集的职责 |
|---|---:|---|
| `services/channel-conversation.mjs` | 8,671 | 意图、会话、资料、任务路由与回执 |
| `services/work-items.mjs` | 8,209 | 任务生命周期、执行、复核、偏好与结果投影 |
| `runtime/service-composer.mjs` | 8,288 | 依赖组装，同时夹杂部分领域流程和存储细节 |
| `services/auto-run.mjs` | 5,129 | 自动执行策略、状态推进、复核和恢复 |
| `features/tasks/work-item-summary-view.tsx` | 3,948 | 任务详情读取、状态解释、操作和大部分展示 |
| `web/src/lib/api-client.ts` | 3,099 | 多个业务域的请求与 DTO |

关键风险：

- 组合器曾直接依赖 JSON 恢复、内存 Store、SQLite 镜像和 SQLite 擦除 API，存储策略变化会扩大到业务组装层。
- 大型领域文件同时承担命令、查询、策略和展示投影，局部修改容易触发远距离回归。
- 前端页面直接理解过多服务端状态，风险提示与可执行动作较难独立迭代。
- 仅靠功能测试难以阻止模块重新跨层引用，需要把依赖方向变成自动检查。

## 目标依赖方向

服务端依赖只允许由外向内：

```text
HTTP 路由
  -> 应用用例 / 领域服务
    -> Store、事件、时钟、执行器等端口
      -> SQLite、JSON 迁移、Bridge、外部连接器等适配器

runtime/service-composer.mjs 只负责创建对象和连接端口，不实现领域规则。
```

前端依赖方向：

```text
页面壳与路由
  -> feature controller / hooks
    -> 按业务域拆分的 API client
      -> 共享 HTTP transport
```

状态来源约束：

- 运行时内存 `state` 继续作为当前进程的读写投影。
- 正常持久化运行默认以 SQLite 为权威介质；旧 JSON 仅用于首次迁移、显式导出，以及 SQLite 不可用时的降级路径。
- 展示凭据与长期幂等台账保持分离，不能因 UI 保留上限淘汰幂等事实。
- 连接器、本地台账和“我的资料”通过显式归属与引用关联，不复制成多个含义不清的权威副本。

## 分阶段实施

### A. 架构基线与 Store 组合边界

状态：已完成第一批（组合器降至 8,192 行，存储职责迁入独立边界）。

- 新增 `runtime/store-composition.mjs`，集中负责持久化选择、启动恢复、SQLite 播种/水合、增量镜像和历史能力。
- `service-composer.mjs` 只消费 Store 边界返回的能力，不再导入持久化实现，也不直接调用 SQLite 查询和压缩 API。
- 增加架构适配度测试，阻止上述直接依赖回流。
- 保持内存测试路径、JSON 降级路径和 SQLite 正式路径的现有行为。

退出条件：内存、JSON 和 SQLite 关键路径测试通过；组合器不存在直接持久化实现依赖；现有 API 无变化。

### B. SQLite 启动与崩溃安全

状态：进行中（启动/降级/关闭生命周期已收口，正式 Store 提交的 `SIGKILL` 恢复测试已建立）。

- 将数据库打开、迁移、完整性检查和关闭收口为一个生命周期组件。
- 增加异常中止、WAL 恢复、重复启动、迁移失败和降级告警测试。
- 明确迁移完成标记，避免旧 JSON 被重复导入。
- 对长期幂等记录设置独立保留策略和索引，不受最近凭据展示上限影响。

退出条件：强制终止后数据可恢复；迁移可重复执行且不重复业务动作；故障时给出结构化诊断。

### C. 任务领域后端拆分

按用户旅程而非按技术函数拆分：

1. `task-command-service`：创建、取消、重试、补跑验证和请求 AI 修复。
2. `task-review-service`：风险、复核证据、验证命令结果和建议动作。
3. `task-result-service`：开发结果、办公批次结果、回滚状态和详情。
4. `task-preference-service`：学习、查看、修改、撤销“我的任务偏好”。
5. `task-read-models`：面向页面的稳定投影，避免页面拼接底层状态。

先提取纯查询和纯策略，再迁移写命令；每次只移动一个用户场景，并保留契约测试。

退出条件：`work-items.mjs` 不再新增职责；任务关键场景可在不启动 HTTP 的情况下做用例测试；路由只做鉴权、校验和响应映射。

### D. Channel 与自动执行拆分

- Channel 只负责接收、澄清、回执和会话上下文；任务执行交给任务应用服务。
- 将意图理解、资料引用、模板选择和任务路由拆为显式决策结果，保留“为什么这样理解”的证据。
- 自动执行策略、调度、恢复、复核分别形成端口，所有制动器复用同一策略入口。

退出条件：同一任务从 Web、Channel 或模板发起时复用相同命令和风险语义；失败恢复不会重复外部动作。

### E. 任务前端垂直切片

- 把任务摘要页拆为概览、风险与证据、开发动作、办公批次、偏好说明五个可独立测试区块。
- API client 按任务、资料、模板、Channel 等业务域拆分，共享认证与错误映射。
- 服务端提供动作可用性与原因，前端不重复推导权限和风险规则。

退出条件：普通用户能在一个视图内理解“发生了什么、为什么有风险、现在能做什么”；开发类和办公类动作互不干扰。

### F. 持续架构门禁

- 为禁止依赖、循环依赖、公开 API 契约和关键模块体积设置 CI 检查。
- 体积目标作为迁移方向：组合器低于 3,000 行，单个领域服务低于 1,500 行，单个任务页面低于 1,200 行；迁移期间先禁止热点继续增长，再逐批降低上限。
- 每个批次记录行为契约、数据迁移、回滚方式和普通用户场景证据。

## 开发顺序

1. 完成 Store 组合边界和架构测试。
2. 加固 SQLite 生命周期、迁移与崩溃恢复。
3. 从任务“风险复核与动作可用性”读模型开始拆后端。
4. 接入开发动作和办公批次的统一命令/结果模型。
5. 拆任务页面和 API client。
6. 再迁移 Channel 与自动执行，避免同时改动所有入口。

## 每批验证要求

- 单元：新增边界的正常、降级和失败路径。
- 契约：旧路由响应与状态语义保持兼容。
- 集成：SQLite 重启、幂等、删除与恢复。
- 用户旅程：开发任务、办公批次、Channel 发起、资料/模板引用各至少一个真实场景。
- 工程：类型检查、仓库健康检查、文档链接检查和差异格式检查。

只有本批退出条件全部满足后，才删除旧路径；不以“大文件已经拆开”代替行为验证。
