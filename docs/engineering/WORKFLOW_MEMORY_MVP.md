# 交付工作流记忆 MVP

关联 Issue：[#1547](https://github.com/perly6185-lab/myagenttool/issues/1547)

## 产品目标

用户授权一个项目内目录后，系统从历史需求文件和已交付文件中形成可解释的工作流画像。以后新需求文件进入目录时，系统推荐合适画像，列出已识别和缺失的信息，经用户确认后创建本地任务，并用实际产物与用户反馈持续校正画像。

MVP 不把“相邻文件”直接当成事实，也不让模型静默学习全部磁盘内容。文件角色、需求—交付关系和最终验收都保留人工确认点。

## 用户工作流

1. 在“资产”中进入“交付记忆”。
2. 选择项目和项目内目录；桌面端可以直接使用系统目录选择框。
3. 扫描后查看系统建议的文件角色和判断依据，确认需求、交付、参考资料或草稿。
4. 确认“需求 → 交付”的真实案例。一个需求可对应多个交付，一个交付案例也可包含多个需求文件。
5. 使用已确认案例生成工作流画像。少于三个案例为“试用”，三个及以上为“正式”。
6. 新需求出现在收件箱后，查看推荐画像、已识别字段和缺失字段。
   推荐同时展示相似的已确认案例、相似度和命中依据，不返回原始文件正文。
7. 补齐必要信息后创建交付任务。任务保存所用画像族、版本、需求事实和计划输出。
8. 可以选择一个可用 Agent 启动受治理的自动交付。执行复用项目 Auto-run 的独立工作树、并发限制、审批和任务认领，不会另起一套绕过治理的执行器。
9. 界面轮询展示 Auto-run 状态；执行中可以取消，失败或阻塞后可以在原工作树重试。取消后也可以重新开始，新尝试使用独立工作树，并保留旧尝试。
10. 在执行记录中可以进入任一工作树查看完整改动，对比最近两次尝试的文件变化，并显式清理旧工作树。
    对比可以展开到逐文件统一 Diff；成功尝试可以被明确选为最终验收来源。
11. 产物完成后运行验收，再由用户给出最终反馈。接受的结果会成为新的确认案例。
12. 如果接受的产物仍在独立工作树中，先预览目标路径和冲突，再显式勾选确认发布；系统不会覆盖项目中的已有文件。发布完成后才把结果纳入学习。
13. 发现历史配对错误时可以撤销案例；画像不会被静默修改。用户从当前有效案例生成草稿，查看字段、章节、输出和影响变化后再显式发布。

## 领域关系

```text
Project
└── WorkflowSource（用户授权的项目内目录）
    ├── WorkflowArtifact（文件快照 + 角色建议/确认）
    ├── DeliveryCase（已确认的需求文件 N ↔ 交付文件 N）
    ├── WorkflowProfile family
    │   ├── v1（归档后不可修改）
    │   └── v2（当前版本）
    └── WorkflowRun
        ├── 输入需求快照与补充事实
        ├── 固定的画像版本
        ├── LocalWorkItem
        ├── ExecutionAttempt 1 → AutoRun + Worktree + Agent
        ├── ExecutionAttempt 2 → AutoRun + 新 Worktree + Agent
        ├── 计划输出与验收结果
        └── 用户反馈
```

## API

基础路径为 `/api/workflow-memory`。

- `GET|POST /sources`：查询或授权来源
- `POST /sources/:id/scan`：增量扫描
- `POST /sources/:id/cancel-scan`：取消正在进行的扫描
- `POST /sources/:id/revoke`：撤销授权
- `POST /sources/:id/delete-learning-data`：在撤销后删除派生数据，不删除原始文件
- `POST /sources/:id/index-embeddings`：增量构建可选本地向量索引并执行启用门禁
- `GET /sources/:id/pair-proposals`：查询可解释的配对建议
- `GET /artifacts`、`POST /artifacts/:id/confirm`：查询并确认文件角色
- `POST /artifacts/:id/retry-extraction`：重试单个文件的受限内容解析
- `GET|POST /cases`：查询或确认交付案例
- `POST /cases/:id/archive|restore`：撤销或恢复学习案例
- `GET|POST /profiles`：查询或从案例生成画像
- `POST /profiles/:id/revisions`：创建画像新版本
- `GET /profile-drafts`、`POST /profiles/:id/drafts`：查询或从有效案例重建画像草稿
- `POST /profile-drafts/:id/publish`：审核后显式发布画像草稿
- `GET /inbox`：查询未配对的新需求
- `GET /inbox/:artifactId/matches`：匹配画像
- `GET /inbox/:artifactId/similar-cases`：查询可解释的相似历史案例
- `GET /inbox/:artifactId/inspect`：检查需求信息完整性
- `GET /retrieval-evaluation`：查看来源级离线检索评测和向量灰度门禁
- `GET|POST /runs`：查询或创建交付任务
- `POST /runs/:id/execute`：选择 Agent 并启动受治理的 Auto-run
- `POST /runs/:id/cancel-execution`：取消仍在执行的 Auto-run
- `POST /runs/:id/retry-execution`：在原工作树重试失败或阻塞的 Auto-run
- `POST /runs/:id/attempts/:number/cleanup`：安全清理非当前尝试的旧工作树
- `POST /runs/:id/attempts/:number/select`：选择一个成功尝试作为最终验收来源
- `POST /runs/:id/validate`：验收计划输出
- `POST /runs/:id/feedback`：记录最终反馈
- `POST /runs/:id/publication-preview`：预览工作树产物的受治理发布目标和冲突
- `POST /runs/:id/publish`：在显式确认后排他发布，不覆盖已有文件

所有修改型接口在更新已有记录时使用 `expectedRevision` 做乐观并发控制。创建交付任务使用“需求指纹 + 画像版本”作为幂等键，重复提交会返回已有任务；同一 WorkflowRun 的重复执行请求只会绑定已有 Auto-run，不会启动第二个任务。

## 安全与隐私边界

- 只允许授权已注册项目的真实子目录；拒绝 `..`、绝对路径和解析后越界的路径。
- 扫描不跟随符号链接，并忽略隐藏目录、版本控制目录、依赖、构建缓存、临时文件、密钥和 `.env`。
- 默认只读元数据；只有用户选择“读取受支持的文本内容”时才读取文本。
- 单文件文本读取上限为 256 KiB，单次最多索引 20,000 个文件、目录深度最多 32 层；同一来源的重复扫描会合并，单设备最多同时运行两个只读扫描。
- 来源可随时撤销；撤销后不能继续扫描或启动基于该来源的新学习流程。
- 文件内容按不可信数据处理。角色建议是确定性信号结果，不执行文件中的指令。
- 已确认文件内容变化后自动转为“需要重新确认”，不会静默改写可信证据。
- 所有查询和操作都按团队/项目访问范围过滤。

## 画像与执行规则

- 画像只使用用户确认的 `DeliveryCase`。
- 案例撤销必须填写原因并保留审计历史；恢复前重新核对全部证据快照，文件变化时拒绝恢复。
- 案例变化不会直接修改当前画像。重建结果先保存为草稿，只有显式发布才会创建新的不可变画像版本；画像基线变化后旧草稿拒绝发布。
- Markdown 的共同字段和共同章节带覆盖率与证据文件 ID，可追溯到来源。
- 正式画像要求至少三个已确认案例；样本不足时可以试用，但界面明确标识。
- 画像修改创建新版本，旧版本归档；已创建任务继续引用原版本。
- 输出路径只能使用受控的相对路径模板，禁止越界和未解析变量。
- 默认覆盖策略为 `never`。验收检查文件存在性和必备 Markdown 章节，并把结果写回工作项验证记录。
- 自动执行前再次核对需求文件指纹和所有计划输出路径；输入发生变化或输出已被其他流程占用时拒绝启动。
- 自动执行要求项目可以创建 Git 工作树，并且所选 Agent 可用且属于任务所在设备。全局/项目执行容量、审批、预算、断路器和任务认领继续由 Auto-run 统一控制。
- `done`、`pr_open` 或报告完成后进入“可以验收”；`failed`/`blocked` 可重试，运行中可取消，需要补充信息或拆解确认时进入“需要处理”。
- WorkflowRun 最多保留最近 20 次执行尝试；每次记录 Auto-run、Agent、工作树、调用链、重试次数、开始/结束时间和结果。取消后重新开始会创建新 Auto-run 和新工作树，旧工作树不被覆盖或删除。
- 尝试详情复用租户隔离的工作树差异接口。界面可以打开完整工作树，也可以并排比较最近两个仍可用工作树的变更文件。
- 旧工作树只允许显式清理，且不能清理当前尝试。清理使用非强制 Git 操作；存在未提交内容时拒绝并保留目录，未合并提交的分支不会被强制删除。清理记录保留在 WorkflowRun 历史中。
- 已选为最终验收来源的尝试同样禁止清理。重新选择会清空旧验收结果，验收和最终反馈记录所选尝试编号。
- 相似案例检索只在当前团队可见的已确认案例中运行，使用路径/正文词元、共同结构字段、格式、来源和已确认反馈形成可解释分数；返回案例元数据和理由，不返回索引正文。
- “修改后符合”会保留实际结果并给出画像修订建议，不会自动覆盖当前画像。

| --- | --- | ---: | --- |
| 1. 统一解析契约 | 文件指纹、解析状态、解析器版本、错误分类、结构化内容和证据位置 | 2–3 日 | 已完成 |
| 2. Office/PDF/HTML 解析 | DOCX、PDF、PPTX、XLSX 和清理版 HTML 的受限解析器 | 5–6 日 | 已完成（首版） |
| 3. 学习链路接入 | 分类、案例配对、画像生成、需求检查和相似检索使用统一解析结果 | 3–4 日 | 已完成（首版） |
| 4. 后台索引任务 | 持久化任务、逐文件检查点、进度、取消、重启恢复、幂等和并发限制 | 3–4 日 | 已完成（首版） |
| 5. 用户体验与回归 | 解析状态、失败说明、排除/重新纳入与重试操作、安全和性能回归 | 2 日 | 已完成（首版） |

建议按以下开发项实施：

1. 统一文档解析与证据定位契约。
2. DOCX 标题、正文和表格解析。
3. PDF 分页文本解析与扫描件识别。
4. PPTX 幻灯片标题、正文和备注解析。
5. XLSX 工作表、表头和受限数据区域解析。
6. 清理版 HTML 正文解析。
7. 多格式内容接入画像与相似检索。
8. 后台索引队列、进度和断点续扫。
9. 普通用户解析状态、排除文件和恢复操作。
10. V1.2 安全、并发、性能与回归验证。

### V1.2 产品与安全规则

- 原始 Office/PDF 文件保留在用户本地；默认只持久化受限的结构化抽取结果、摘要和证据定位，不复制完整原文。
- 每个抽取字段和学习依据可以定位到页码、幻灯片、工作表、单元格区域、表格或段落。
- 解析结果绑定文件指纹和解析器版本；两者都未变化时不重复解析，任一变化时旧结果失效并重新确认。
- 单文件大小、页数、幻灯片数、工作表数、单元格数、抽取文本量和解析时间均设置安全上限。
- 扫描型 PDF 标记为“需要 OCR”，V1.2 不静默猜测无法可靠读取的正文。
- 单文件解析失败不阻塞整个来源；用户可以查看安全化错误、排除文件或显式重试。
- 后台任务按团队、设备和来源限制并发；重复请求幂等，服务重启后可以从安全检查点继续。
- 每个文件解析完成即写入任务检查点；进程重启后未完成任务标记为“可恢复”，再次扫描复用指纹和解析器版本均未变化的结果。
- 排除文件必须填写原因并保留审计事件；排除状态同时作用于配对、案例、画像、新需求和相似检索，重新纳入后必须复核角色。
- 文档内容继续按不可信输入处理，解析器不执行宏、脚本、外链、嵌入对象或文件中的指令。
- 所有解析记录、进度和错误继续遵守项目访问范围与租户隔离。

### V1.2 验收标准

- 同一来源中 Markdown、DOCX、文本型 PDF、PPTX、XLSX 和 HTML 可以被识别并形成统一的结构化证据。
- 画像字段、章节和相似案例理由能够回溯到具体文档位置。
- 未变化文件不会重复解析；变化文件会使依赖它的确认和画像草稿进入需要复核状态。
- 大目录任务可以查看进度、取消、重试，并在进程重启后恢复，不产生重复记录。
- 加密、损坏、超限或扫描型文档得到明确状态，不阻塞其他文件。
- 普通用户无需理解解析器或数据结构即可完成扫描、处理异常和继续生成画像。
- 多租户、目录越界、符号链接、压缩炸弹、资源上限和并发竞争测试全部通过。

### V1.2 暂不包含

- OCR 内容识别和图像文字理解。
- 外部向量数据库或强制云端 Embedding。
- 跨团队共享原始内容或解析正文。
- 自动合并所选工作树或覆盖用户交付文件。

## V1.3 规划：学习质量与可靠交付闭环

V1.3 将产品从“可以学习历史文件”推进到“能够判断学习证据是否可信，并持续验证新交付是否符合历史标准”。预计 10–14 个开发日。

| 阶段 | 交付内容 | 预计工期 | 状态 |
| --- | --- | ---: | --- |
| 1. 学习质量评分 | 案例完整性、证据有效性、解析覆盖率、角色置信度、配对可信度与画像质量汇总 | 2–3 日 | 已完成（首版） |
| 2. 混合相似检索 | 关键词、结构化字段与可选本地向量召回，附命中理由和离线评测集 | 2–3 日 | 已完成（首版） |
| 3. 交付质量验证 | 路径、格式、必需章节、字段、附件与阻断/建议分级 | 2–3 日 | 已完成（首版） |
| 4. 反馈学习闭环 | 接受、修改后接受、拒绝、差异和原因形成可审核画像草稿 | 2 日 | 已完成（首版） |
| 5. 受治理发布 | 目标目录预览、禁止静默覆盖、显式确认和完整发布审计 | 2–3 日 | 已完成（首版） |

### V1.3 阶段 1 已实现

- 每个确认案例动态计算 0–100 学习质量分，状态为“可信”“需复核”或“已阻断”。
- 评分由证据完整性、需求—交付配对可信度、可解析内容覆盖率和角色确认度共同组成。
- 文件缺失、变化或被排除会立即阻断案例；解析不完整、角色未确认或低配对可信度会给出普通用户可理解的复核原因。
- 相似案例只使用未阻断的学习案例，并对可信案例增加有解释的排序权重。
- 画像汇总可信、待复核和阻断案例数；只有至少三个可信案例才能形成正式画像。
- 执行前重新计算画像质量，阻断画像不能继续创建交付任务。

### V1.3 阶段 2 已实现

- 相似案例返回统一、版本化的评分明细：文本相似、结构化字段、格式、学习质量、来源、用户反馈和预留向量通道。
- 检索响应明确报告策略版本、当前模式、向量是否启用，以及无向量时的确定性降级能力。
- 来源级离线评测使用已发布画像家族作为相关性真值，计算 Top-1、Top-5、MRR 和无结果率。
- 新策略与不含学习质量/向量增益的基线进行同样本比较；样本不足或指标回退时，不允许进入本地 Embedding 启用阶段。
- 普通用户界面展示样本量、Top-1、Top-5、MRR 和门禁结论，不要求理解向量或检索实现。

阶段 2 还包括：

- 可插拔本地 HTTP Embedding 适配器；运行时依赖注入仍允许替换为其他本地实现。
- 默认关闭，且只接受无凭据的 `http://127.0.0.1`、`localhost` 或回环 IPv6 地址，不允许把原文发送到远程服务。

- 增量构建复用指纹、提供方和模型版本均未变化的记录；变化、排除、删除或模型升级只重建受影响记录。

- 灰度比例通过团队、来源和模型版本计算稳定桶；未命中灰度、门禁失败、索引缺失或本地模型不可用时继续使用确定性结构化/关键词检索。

### V1.3 阶段 3 已实现

- 交付验收使用版本化验证契约，当前 `validatorVersion` 为 2；每项结果包含稳定规则、阻断级别、状态、目标文件、期望值、实际值和可选证据。
- 阻断项覆盖：路径存在且仍位于项目或所选执行工作树内、文件非空、受支持二进制格式签名、Office/PDF/HTML 可解析状态、JSON/YAML 语法、CSV 表头、画像要求的章节和字段、最少输出数量、Markdown 本地附件，以及计划时未覆盖已有文件。
- PDF 扫描件或解析达到安全上限时给出警告，不把不完整解析伪装成通过；损坏文件和格式签名不一致会阻断验收。
- 历史可信交付不少于 3 个时，对同格式产物执行宽松的体量异常检查；样本不足会明确显示“数据不足”，但不会阻断用户继续验收。
- 只要任一阻断项失败，运行进入 `validation_failed`；纯警告仍可进入人工接受。运行保存阻断数、警告数、检查时间和验证器版本。
- 验收默认读取用户明确选择的成功执行尝试对应工作树，不会误读项目主目录中的旧文件。
- 工作项只接收其计划内的稳定验收条件，动态明细保留在 WorkflowRun；已验证的本地产物路径和大小作为工作项证据记录，回写失败会产生审计事件。
- 普通用户界面按通过、警告和阻断分色展示，并显示具体文件和可理解的原因，不要求用户阅读原始验证 JSON。
- 文件内容读取限制为 512 KiB 前缀；文档解析继续沿用 Office/PDF 的大小、页数和展开量限制。本地附件会进行真实路径约束，拒绝目录越界、符号链接逃逸、缺失文件和异常 URL 编码。

### V1.3 阶段 4 已实现

- 最终反馈使用版本化契约，当前 `version` 为 1，保留反馈类型、原因分类、文字说明、操作者、时间、所选执行尝试、学习状态和关联案例/画像草稿。
- “符合预期”保持一键确认；“修改后符合”和“不符合预期”必须选择原因并填写说明。原因包括内容修正、结构调整、格式调整、信息缺失、质量问题、工作流不匹配和其他。
- 每次验收保存产物 SHA-256、大小、修改时间、章节和字段快照，不保存额外原文。反馈时重新读取所选执行工作树并执行阻断验证。
- 普通接受发现验收后文件发生变化时会拒绝静默纳入，提示改用“修改后符合”或重新验收；修改后接受仍须通过文件、结构和附件阻断门禁。
- 修改差异按文件记录前后哈希与大小，以及章节/字段的新增和删除。拒绝反馈同时保存当时未通过或警告的验证项，形成可追溯原因证据。
- 已发布到授权来源且能够重新索引的接受结果会创建新的确认案例；普通接受直接加入学习证据，修改后接受会自动从当前有效案例重建画像草稿。
- 自动生成的画像草稿记录触发它的运行、原因、说明和差异摘要，但不会自动发布。用户仍需查看结构变化和影响后显式发布。
- 只存在于执行工作树、尚未发布到授权来源的结果会记录为“发布后再纳入学习”，不会伪造来源文件或因索引不到主目录而丢失反馈；V1.3 阶段 5 发布后负责完成证据落地。
- 拒绝结果标记为“不纳入学习”，不会创建成功案例或修改画像。来源扫描失败、需求证据变化和案例创建失败会显示独立的等待或阻断状态。
- 同一运行的并发反馈使用运行级互斥和乐观版本检查；反馈、草稿关联及学习状态写入审计事件。
- 普通用户界面提供原因下拉框、说明输入、反馈学习状态、验收后变更数量，并在画像草稿中显示由哪次“修改后符合”触发。

### V1.3 阶段 5 已实现

- 只有已经完成人工接受、且反馈学习状态为“发布后再纳入学习”的运行可以进入文件发布；拒绝结果、尚未验收结果和已直接位于目标目录的结果不能误走发布流程。
- 发布分为两个独立动作：先生成版本化预览，再提交与该预览 ID、摘要和运行版本绑定的显式确认。未勾选确认、旧预览或并发请求都会被拒绝。
- 预览显示所选执行尝试、每个项目相对目标路径、文件大小、SHA-256、目标是否可用以及文件/目录/符号链接冲突；不向客户端暴露额外绝对路径。
- 预览和正式发布都会重新核对来源工作树、目标项目、租户权限、路径边界和符号链接。验收反馈之后发生的任何来源文件变化都会阻止生成预览。
- 已存在的文件、目录、符号链接和发布过程中突然出现的目标都会视为冲突，不提供覆盖选项，也不通过普通重命名覆盖用户内容。
- 正式发布先在每个目标目录创建排他暂存文件，核对大小和哈希，再通过原子硬链接排他创建最终文件。任一文件失败时，只回滚本次创建且 inode 仍匹配的文件，不删除或修改并发产生的用户文件。
- 发布状态依次记录为 `previewed`、`publishing`、`published` 或 `blocked`。显式确认在文件写入前持久化；若进程中断，重试可以识别哈希一致的已发布文件和暂存文件并继续剩余文件。
- 发布审计记录预览摘要、文件数、冲突数、来源尝试、确认人、确认时间、发布人、发布时间、失败原因和最终文件哈希。
- 发布成功后自动重新扫描授权来源。能够定位全部目标文件时，阶段 4 的等待反馈会创建确认案例；“修改后符合”还会生成带差异与原因的画像审核草稿。来源不覆盖目标目录时会明确阻断学习，不伪造证据。
- 普通用户界面提供目标文件列表、大小、冲突状态、来源尝试、确认复选框和发布状态；没有显式勾选时“确认发布”按钮保持不可用。
