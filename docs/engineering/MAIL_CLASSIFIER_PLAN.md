# 邮件智能分拣器实施计划

状态：M0–M8C 与 M8D-1/M8D-2 已实现（2026-08-18）；M8D-3 等待真实测试账号完成连续 7 个自然日
面向版本：邮件客户端阶段五
首要用户：每天收到大量邮件、希望先看到待处理事项，但不了解过滤规则或 AI 配置的普通用户
关联文档：[我的邮箱 MVP 计划](MAIL_CLIENT_MVP_PLAN.md)、[ADR 0011](ADR_0011_MAIL_UNTRUSTED_INPUT.md)、[ADR 0027](ADR_0027_MANAGED_MAIL_ARCHIVE.md)

## 1. 结论先行

邮件分拣器采用“邮件头快速分拣 + 正文按需精分 + 人工纠正”的两阶段架构。

- 默认只分析已经同步到本地控制面的邮件头，不批量下载正文或附件。
- 确定性分类始终可用；语义模型是可选增强，失败时不影响收件和阅读。
- 分类结果本身只生成智能视图、标签和操作建议；真实目录整理是独立、默认关闭的写能力。手动整理需查看完整批次并逐次确认；只有稳定性达标且用户另行确认的低风险目录规则可在同步后自动移动最多 10 封。分类不会自动删除、回复、转发邮件或创建任务。
- 所有邮件始终保留在“全部邮件”和服务商原文件夹中；误分类不能造成邮件消失。
- 用户纠正优先于机器结果，后续重新分类不得覆盖人工决定。
- 正文语义分类必须先补充安全 ADR，并由用户明确开启；默认关闭。

第一版的目标不是“替用户管理邮箱”，而是把 100 封混杂邮件压缩成几个容易理解的入口：

1. 待处理
2. 重要信息
3. 通知与回执
4. 订阅与推广
5. 其他

当前已落地的纵向切片覆盖：白名单邮件头、确定性分类、持久化结果与任务记录、`new_mail` / `rebuild` 两种基础整理、智能视图、解释、不确定提示、带版本校验的人工纠正，以及 [ADR 0028](ADR_0028_MAIL_SEMANTIC_CLASSIFICATION.md) 约束下的本机正文精分。基础整理在单次本地事务内完成；深度整理采用最多 50 封、并发 2 的异步任务，支持进度、取消、熔断和重启后中断标记。M5C/M5D 已增加显式自动目录规则、逐封结果、冲突暂停、同步后核对、恢复预览和操作历史；M6 已增加不含邮件内容的本地质量看板和样本门槛；M7 已把最多 10,000 封缓存邮件的文件夹、分类视图、搜索、排序和分页迁入独立 SQLite 查询索引。

## 2. 问题定义

当前邮箱已经支持文件夹、分页、搜索、已读状态、附件、草稿、发送和邮件转任务，但用户仍需逐封判断：

- 哪些邮件需要回复或继续处理；
- 哪些只是系统通知、账单回执或订阅内容；
- 哪些邮件可能与客户、项目或账号安全有关；
- 哪些邮件可以稍后阅读。

服务商文件夹不能解决这个问题。它描述邮件存放位置，不描述用户下一步该做什么；搜索则要求用户预先知道要找什么。分拣器应降低浏览成本，同时避免把错误判断变成自动化副作用。

## 3. 范围与非目标

### 3.1 本计划交付

- 对最多 10,000 条本地可见邮件头进行可恢复、可重复的批量分类。
- 提供稳定的分类协议、版本、置信度、理由码和人工确认状态。
- 在邮箱中提供智能视图、分类标签、解释和一键纠正。
- 支持用户主动发起的有限正文精分，并明确展示范围、隐私和资源影响。
- 记录分类覆盖率、纠正率、未知率、延迟和可选模型用量。
- 仅根据本租户的多次一致纠正建议个人规则；启用前必须由用户查看影响并确认，且不执行邮件动作。
- 根据已启用的低风险个人规则建议服务商目录；目标目录与影响清单必须由服务端按当前邮箱状态重算，预览最多 50 封并明确排除重要、待处理及账号安全邮件。
- 支持用户在质量稳定后单独启用低风险目录自动规则；每次同步后每条规则最多移动 10 封，任一不确定结果立即暂停。
- 提供逐封结果、同步后核对、仅针对仍在原目录邮件的恢复预览，以及最近 50 次有界操作查询记录。

### 3.2 首版不做

- 不因分类结果本身自动移动邮件；仅允许用户另行启用、受质量门控的低风险目录规则执行有界移动。
- 不自动标为已读、删除、归档、退订或举报垃圾邮件。
- 不自动回复、转发、创建任务或下载附件。
- 不把“紧急”分类当成可靠告警渠道。
- 不训练自有模型，也不使用其他租户的邮件或反馈。
- 不提供复杂规则编辑器、多账号统一收件箱或团队共享分类规则。

## 4. 不可突破的现有边界

### 4.1 邮件内容始终是不可信数据

分类器不得把主题、正文、发件人名称、附件名或 HTML 当成指令。语义分类提示必须将所有邮件字段放入明确的数据边界，分类代理不得持有工具、文件、网络、发件或任务写入能力，只允许返回受约束的 JSON。

检测到提示注入信号时：

- 保留原始邮件，不清洗或改写证据；
- 记录 `prompt_injection_signal` 理由码；
- 分类仍可降级完成，避免攻击者用特殊文本阻断整个收件箱；
- 结果不得触发任何自动动作。

### 4.2 后台同步继续保持邮件头优先

现有同步有意只获取有界邮件头。第一阶段分类必须复用这些本地字段，不得为了“智能”静默批量下载正文、附件或远程图片。

### 4.3 正文精分是新的数据处理边界

ADR 0011 禁止在邮件转录步骤让模型理解原始正文；ADR 0027 又把显式打开邮件定义为本地归档边界。因此在实现正文精分前，必须新增安全 ADR，明确：

- 是只分析已打开、已缓存的正文，还是允许用户主动批量获取；
- 使用本地模型还是外部模型，哪些字段可能离开设备；
- 正文截断、临时缓存、存档增长和删除策略；
- 模型无工具隔离、提示注入处置和审计字段；
- 用户关闭语义分类后如何停止任务和处理派生结果。

在该 ADR 被接受前，产品只交付邮件头分类。

### 4.4 分类不是授权

`suggestedAction=reply` 或 `suggestedAction=create_task` 只用于界面提示。真正回复和转任务必须继续走现有草稿、revision、人工复核和任务材料边界。

## 5. 用户可见分类

### 5.1 智能视图

| 智能视图 | 用户含义 | 进入条件 |
| --- | --- | --- |
| 待处理 | 可能需要回复、确认、提交材料或采取行动 | `attention=action_required` 或 `attention=reply_expected` |
| 重要信息 | 值得优先阅读，但尚不能确定需要动作 | `attention=important` |
| 通知与回执 | 系统通知、订单/支付回执、物流、日历和账号事件 | 对应 `mailType` 且不属于待处理 |
| 订阅与推广 | Newsletter、营销和低优先级群发内容 | `mailType=newsletter` 或 `marketing` |
| 其他 | 信息不足或无法可靠判断 | `attention=routine` 或 `unknown` |

“全部邮件”始终是默认安全兜底。智能视图是同一批邮件的派生过滤器，不改变服务商文件夹。

### 5.2 内部分类协议

分类采用多维结果，不把业务主题和注意力等级混成一个互斥标签：

```json
{
  "attention": "action_required | reply_expected | important | routine | low_value | unknown",
  "mailType": "human_conversation | customer_or_project | transaction | account_security | calendar | system_notification | newsletter | marketing | personal | other | unknown",
  "suggestedAction": "reply | create_task | review_attachment | read | archive_candidate | none",
  "confidence": 0.0,
  "reasonCodes": ["direct_recipient", "reply_language"],
  "explanation": "发件人直接询问交付范围，可能需要回复。"
}
```

协议约束：

- `attention`、`mailType` 和 `suggestedAction` 使用关闭枚举。
- `reasonCodes` 使用可测试的关闭词表；最多 8 个。
- `explanation` 是给用户看的短句，最多 160 个字符，不复制正文中的敏感内容。
- `confidence` 只用于门槛和“不确定”提示，不在普通界面展示小数。
- 日期、金额、联系人、摘要等实体提取不属于分类协议，避免首版变成通用邮件理解系统。

### 5.3 置信度策略

- `>= 0.85`：显示建议分类。
- `0.60–0.84`：显示建议分类并标记“可能不准确”。
- `< 0.60`：归入“其他”，内部保留候选结果用于评估。
- `account_security`、`action_required` 和 `reply_expected` 不允许因为低置信度而隐藏邮件，只能影响排序或建议视图。

阈值必须通过离线评测数据调整，不能直接依据开发样例固化。

## 6. 两阶段分类流水线

### 6.1 阶段 A：邮件头确定性分拣

输入仅限控制面已有字段：

- 账号与服务商的非敏感标识；
- Message-ID 的账号作用域派生键；
- 发件人地址与显示名；
- 主题；
- 日期、服务商文件夹、已读状态；
- 是否已获取正文、是否有附件元数据。

规则示例：

- `no-reply`、`noreply`、`notification` 等地址模式；
- `List-Unsubscribe`、`List-Id`、`Auto-Submitted`、`Precedence` 等安全邮件头；
- 账单、验证码、订单、物流、日历等稳定主题信号；
- 直接问句、回复/转发线程、明确期限等弱行动信号；
- 用户明确纠正过的精确发件人或域名规则。

为了提高可靠性，邮件同步协议需要增加一组经过白名单和长度限制的结构化邮件头。不得把任意原始 header map 直接写入状态或返回给 Web。

阶段 A 的特性：

- 不调用模型，不增加外部数据传输；
- 对相同输入和分类器版本产生相同结果；
- 可在新邮件同步完成后增量运行，也可对历史邮件批量重建；
- 无法判断时返回 `unknown`，不勉强分类。

### 6.2 阶段 B：正文语义精分

阶段 B 默认关闭，仅处理以下范围之一：

1. 用户已经打开且正文已在本地可用的邮件；
2. 用户在“深度整理”确认页中明确选择的最近邮件范围。

建议批次上限：

- 每次最多 50 封；
- 单封最多 20,000 字符纯文本；
- 单批最多 500,000 字符；
- 并发 2；
- 单封超时 8 秒，整批可取消并可恢复；
- 不读取附件内容，不加载远程图片，不执行 HTML。

处理顺序：

1. 确定性分类先生成基线结果。
2. 对允许的正文执行长度限制、控制字符归一化和提示注入检测。
3. 使用无工具、结构化输出的分类适配器生成候选结果。
4. 服务端严格解析枚举、长度和置信度；非法输出直接降级到阶段 A。
5. 仅当语义结果提高可解释性且通过门槛时合并；否则保留确定性结果。
6. 持久化派生分类，不持久化模型原始响应或完整提示。

模型不可用、超时、熔断或额度不足时，批次标记为 `degraded`，收件箱继续使用阶段 A 结果。

### 6.3 增量、幂等与线程一致性

分类键应由以下内容生成：

```text
accountId + folderId + messageId + inputFingerprint + classifierVersion
```

- 相同键重复执行直接复用结果。
- 主题、正文版本或关键邮件头变化时生成新 fingerprint。
- 人工确认/纠正状态独立保存，不被重算覆盖。
- 同一线程可提供上下文信号，但每封邮件仍保留独立结果；首版不做整线程摘要。
- 旧分类器版本结果可继续展示，后台分批迁移，不能阻塞邮箱加载。

M4 新增 `mailClassificationCorrections` 与 `mailClassificationRules`。纠正证据以租户、账号和消息键去重，只保存规范化发件地址/域名及关闭枚举目标；规则包含 `accountId`、`matchKind=sender|domain`、匹配值、目标、`active|paused|revoked` 状态和 revision。优先级固定为“单封人工纠正 > 精确发件人规则 > 域名规则 > 语义/邮件头结果”。

存储约束：

- 所有记录按租户隔离；消息身份必须包含账号作用域，不能只依赖 Message-ID。
- 分类记录每租户最多 20,000 条，淘汰时优先删除已不存在邮件的旧机器结果，不删除人工反馈。
- Job 每租户最多 200 条；活跃 Job 不得被淘汰。
- 不保存完整模型请求、响应、邮件正文或邮箱地址到事件日志。
- `provider/model` 仅用于可观测性；普通用户界面不暴露内部代理名称。

## 8. 服务端与 API 计划

### 8.1 服务拆分

- `mail-classification.mjs`：协议归一化、持久化、人工纠正和查询。
- `mail-header-classifier.mjs`：纯函数确定性分类器。
- `mail-classification-jobs.mjs`：批处理、取消、恢复、并发和进度。
- `mail-semantic-classifier.mjs`：可选模型适配器、结构化输出、超时和熔断。
- `mail-classification-result.mjs`：模型完成结果的最小化与安全导入。

不要把分类逻辑继续堆入 `mailbox.mjs`。邮箱服务只负责把分类摘要投影到普通用户读模型。

### 8.2 API 草案

```text
GET  /api/mailbox?view=all|needs_attention|important|notifications|subscriptions|other
GET  /api/mailbox/classification-summary
POST /api/mailbox/classification-jobs
GET  /api/mailbox/classification-jobs/:id
POST /api/mailbox/classification-jobs/:id/cancel
PATCH /api/mailbox/messages/:messageId/classification
GET  /api/mailbox/classification-rules
POST /api/mailbox/classification-rules
PATCH /api/mailbox/classification-rules/:id
```

写接口约束：

- 启动作业只接受服务端定义的 `scope`、`mode` 和有界数量，不接受自由提示词。
- 纠正接口接受关闭枚举、`expectedRevision` 和操作类型，使用乐观并发控制。
- 规则创建只接受服务端当前生成的建议 ID 和 `confirmed=true`；规则更新只接受关闭枚举及暂停、恢复、撤销动作，并使用 revision 校验。
- Message-ID 通过 URL 传递时仍需账号和租户作用域解析；查不到或跨租户统一返回 404。
- 不提供“执行建议动作”的分类 API。

### 8.3 邮箱读模型扩展

每封邮件只增加普通用户所需摘要：

```json
{
  "classification": {
    "attention": "action_required",
    "mailType": "customer_or_project",
    "suggestedAction": "reply",
    "label": "待回复",
    "explanation": "对方直接询问交付范围。",
    "uncertain": false,
    "confirmationState": "proposed",
    "revision": 2
  }
}
```

内部 provider、model、prompt-injection 信号和原始 reason codes 不默认进入普通邮箱列表；详情与管理页可通过受控端点读取必要审计信息。

## 9. 普通用户体验

### 9.1 默认体验

- 首次进入仍显示“全部邮件”，不强迫用户先配置 AI。
- 邮件同步后，确定性分拣在后台快速完成，顶部出现“待处理 8”等智能入口。
- 列表行最多显示一个主标签，避免彩色标签淹没主题和发件人。
- 打开邮件可看到一句“为什么这样分类”，并提供“分类不对”。
- 不确定结果显示为“可能需要处理”，而不是伪装成确定事实。

### 9.2 深度整理

入口文案使用“深度整理最近邮件”，不使用“运行分类 Agent”。确认页必须展示：

- 将处理多少封、哪个时间范围；
- 是否需要读取尚未打开的正文；
- 是否使用外部模型，数据是否离开设备；
- 预计用量或额度影响；
- 不会自动移动、删除或发送邮件；
- 可随时取消，已完成结果会保留。

### 9.3 纠正反馈

“分类不对”提供三个普通操作：

1. 改到另一个智能视图；
2. 以后将这个发件人视为同类；
3. 仅纠正这一封。

第二项由 M4 以显式建议实现：同一精确发件人至少 2 封一致纠正，或同一域名至少 3 封且来自至少 2 个不同地址的一致纠正，才产生建议。启用前展示当前影响数量和最多 5 个样例；启用后仅改变派生智能视图，且单封人工纠正始终优先。用户可修改、暂停、恢复或撤销规则。

### 9.4 批量操作

分类首版只改善浏览。后续如增加批量归档、标已读或转任务，必须采用“勾选邮件 → 预览精确目标 → 明确确认”的独立能力，不能因分类器高置信度而跳过确认。

## 10. 可观测性、成本与隐私

### 10.1 记录的指标

- `mail_classification_coverage_rate`
- `mail_classification_unknown_rate`
- `mail_classification_correction_rate`
- `mail_classification_header_latency_ms`
- `mail_classification_semantic_latency_ms`
- `mail_classification_job_failure_rate`
- `mail_classification_semantic_usage`（请求数、输入/输出量和成本）
- `mail_classification_circuit_open_total`

指标按租户聚合，日志不得包含主题、发件人、正文、附件名或模型原始输出。

### 10.2 预算与降级

- 确定性阶段没有模型成本，始终可用。
- 语义阶段尊重现有 AI 配额、用量计量和取消语义。
- 并发默认 2；连续 3 次提供商失败后熔断 30 秒。
- 达到预算、超时或无可用模型时，界面明确显示“已完成基础整理，深度判断暂不可用”。
- 不允许为了追求覆盖率自动扩大用户确认的邮件范围。

## 11. 测试策略

### 11.1 单元与契约测试

- 关闭枚举、长度上限、置信度归一化和非法模型输出拒绝。
- 中英文主题、自动发件地址、列表邮件头和常见回执规则。
- 提示注入文本始终作为数据，模型适配器无工具权限。
- 相同 fingerprint 幂等复用；版本变化触发重算。
- 人工纠正不被重算覆盖；revision 冲突返回 409。
- 规则建议阈值、一致性、精确发件人优先于域名、单封人工纠正优先于规则。
- 规则启用必须显式确认；编辑、暂停、恢复、撤销均进行 revision 校验并可回滚。
- 租户、账号和同 Message-ID 隔离。
- 超时、取消、崩溃恢复、熔断与阶段 A 降级。

### 11.2 离线评测集

建立不进入产品状态的去标识化评测集，至少包含：

- 中文和英文各 200 封邮件头样例；
- 每个用户可见类别至少 40 个正例；
- 直接问句、抄送、群发、自动回复、订单、验证码、日历、推广等易混场景；
- 至少 50 个提示注入或社会工程样例；
- 同一线程中意图变化和服务商文件夹差异。

评测集不能使用真实用户邮箱导出物提交到仓库。样例必须合成或完成不可逆去标识化。

### 11.3 端到端旅程

- 新用户无模型配置时也能看到基础智能视图。
- 大邮箱启动分类后可查看进度、离开页面、返回继续、取消和重试。
- 390 px 移动端可切换智能视图、查看理由和纠正分类。
- 语义模型失败时不影响收件、阅读、回复和转任务。
- 纠正后邮件立即移动到新的智能视图，但服务商文件夹不变。
- 任何分类结果都不能直接触发发送、删除、移动或任务创建。

### 11.4 性能目标

- 10,000 封邮件头首次确定性分类在开发基准机上 P95 小于 5 秒。
- 新同步 50 封邮件头增量分类 P95 小于 300 毫秒。
- 邮箱首屏不等待分类作业；已有邮件列表 P95 加载回归不超过 10%。
- 分类查询必须在分页前通过索引过滤，不能在 Web 端加载全量邮件后筛选。

## 12. 质量门槛

进入普通用户默认界面前必须满足：

- 待处理视图精确率不低于 90%，召回率不低于 80%。
- 订阅与推广精确率不低于 95%，避免把真人邮件错误降级。
- `unknown` 比率低于 35%，但不得通过降低安全门槛强行达标。
- 人工纠正率低于 15%；高于该值时保持 Beta 标识并禁止扩展自动化。
- 100% 的人工纠正经过重算、重启和同步后仍保留。
- 100% 的模型失败样例安全降级，邮箱基础能力不受影响。
- 安全评审确认不存在分类到副作用的隐式通路。

以上阈值先在合成评测集和内部试用中验证，再用明确同意的本地匿名聚合指标校准；不能上传真实邮件内容做遥测。

交付：

退出条件：样本不足、规则变更、目标冲突和不确定回执均不能静默移动；普通用户能理解持续授权范围并能找到暂停/撤销入口。

退出条件：不确定结果不会重复移动，恢复范围不能由客户端伪造，跨租户不可见，冲突原因和下一步对普通用户可理解。

### M8：真实邮箱试运行与持续性能

交付状态：进行中；M8A–M8C、M8D-1 和 M8D-2 已实现并通过自动化门禁；M8D-3 的真实 7 天计时尚未完成，自动整理继续默认关闭。执行方法与每日证据格式见 [M8 发布与试运行手册](MAIL_M8_RELEASE_RUNBOOK.md)。

目标：不再扩展新的邮件副作用，先证明 M0–M7 在真实、持续变化的大邮箱中容易理解、性能稳定且能够安全恢复。M8 分四个可独立验收的纵向批次推进。

#### M8A：SQLite 增量维护与一致性自检

交付状态：已实现。

- SQLite schema v2 为每行保存稳定内容摘要；事实指纹变化后构建权威投影差分，只对新增、变化和删除的消息键执行写入，不再删除并重写整个租户索引；
- 邮件排序使用由消息键生成的稳定次序，相同时间戳仍可确定排序，新邮件到达不会令所有旧行仅因数组位置变化而失效；
- 保留首次构建、schema 升级、事实源不连续和校验失败时的全量重建路径；增量失败不得破坏上一份可查询快照；
- 增加行数、消息键/内容摘要和文件夹/智能视图聚合检查；发现逻辑漂移时记录不含邮件内容的本地诊断并自动重建，底层 SQLite 不可用时继续回退原邮箱投影；
- 10,000 封基准中，新增或更新 50 封的索引维护 P95 小于 300 毫秒；变化后的首次查询在返回前完成一致差分，避免为了异步快照而短暂展示旧邮件；
- 覆盖跨租户、删除、移动目录、同 Message-ID、多进程重启、损坏数据库和 schema 升级测试。

退出条件：日常变化不再删除并重写 10,000 行；50 行差分在开发基准机上低于 300 毫秒；故障时可回退并自愈；查询结果与事实源投影在固定差分样例中 100% 一致。当前由增删改差分、事务回滚、逻辑损坏自愈、schema v1 升级、重启复用、租户隔离、10,000 行性能和邮箱已读状态集成测试覆盖。

#### M8B：自动目录规则的长期运行治理

- 自动规则增加最近成功、最近暂停原因、连续成功批次和最近核对时间等普通用户可读状态；不保存主题、发件人或正文；
- 对同步触发做账号级串行和幂等保护，避免重复导入、并发同步或进程重启造成同一批消息重复执行；
- 增加启动时的未完成作业扫描；只做状态核对和暂停，绝不在启动恢复中自动补移动；
- 增加受控“试运行”模式：只计算本次会移动多少封及排除原因，不调用 Provider，也不因此累计真实成功批次；
- 保持现有边界：每规则每次最多 10 封、最多考察 10 条规则、质量或冲突暂停后必须重新授权。

退出条件：重复同步、并发同步、超时、进程退出和 Provider 歧义测试均不会重复移动；用户能从状态页看懂“是否在运行、为何暂停、下一步做什么”。

#### M8C：普通用户试用与恢复体验

- 建立五条桌面与 390 px 端到端旅程：首次连接、从 50 封邮件找待处理、纠正并启用规则、确认自动目录规则、处理一次待核对作业；
- 整理“智能分类”“邮箱目录”“自动整理”三层概念和文案，同一页面不混用“标签、规则、文件夹、分类”等近义词；
- 自动整理启用页固定展示范围、触发时机、单批上限、排除对象、暂停/撤销入口和“不会删除/发送”的边界；
- 待核对流程提供单一主操作：先同步核对；核对后只对仍在原目录的邮件开放新的恢复确认；
- 完成键盘操作、焦点回收、屏幕阅读器名称、状态播报、空状态、慢同步和离线错误验收。

退出条件：未阅读技术文档的试用者能在两分钟内完成核心查信任务，能正确说出分类与真实目录的区别，并能独立暂停自动整理和处理待核对状态。

#### M8D：发布证据与渐进开放

- 固化不含真实用户邮件的中英文合成评测集和提示注入集，生成可重复的版本化基线报告；
- 将第 12 节质量门槛、M8A 性能预算和 M8B 重复移动安全断言纳入发布检查；
- 先通过功能开关仅开放只读分类，再开放手动目录整理，最后按账号开放自动规则；任一阶段可独立回退；
- 本地只记录聚合质量、耗时、失败类型和恢复结果；不上传邮件主题、地址、正文、附件名或消息标识；
- 完成至少一个测试账号的连续 7 天试运行记录，覆盖正常同步、断网、凭据失效、重启和冲突恢复。

退出条件：评测、性能、安全、无障碍和连续试运行证据齐全；无重复移动、跨租户泄漏或不可恢复作业；未达到门槛时保持 Beta 和自动整理默认关闭。

#### M8 实施顺序与切分

1. M8A 先行，建立增量索引协议、差分测试和性能基线。
2. M8B 在增量索引稳定后接入同步触发和启动恢复，避免同时改变两个事实维护链路。
3. M8C 与 M8B 后半段并行补齐普通用户旅程，但不提前放宽自动化门槛。
4. M8D 最后汇总发布证据并执行 7 天试运行；发现问题回到对应批次修复，不以人工说明替代产品恢复能力。

开发执行门槛：

2. M8B-3 合并且重复移动安全测试通过后，才允许进入 M8C 自动整理旅程验收。
3. M8C 三项完成前，只能进行只读分类和手动整理的内部测试，不能开放自动整理。
4. M8D-1、M8D-2 全绿后开始 M8D-3；7 天内任何重复移动、不可解释暂停或不可恢复冲突都使计时清零，修复后重新开始。
5. M8D-3 通过后才把 M8B、M8C、M8D 标记完成；此前产品保持 Beta，自动整理保持默认关闭。

## 15. 需要在实施前确认的产品决策

以下决策不会阻塞 M0–M2，但会影响 M3：

1. 语义分类是否坚持仅使用本地模型，还是允许用户选择外部模型。
2. “深度整理”是否允许获取未打开邮件正文，还是只处理已缓存正文。
3. 多账号上线时，智能视图是按账号隔离还是提供显式统一入口。
4. 用户纠正是否只形成个人规则，还是允许团队管理员发布共享规则。

默认建议：首版只做单账号、本地邮件头分类；正文仅处理已打开缓存，外部模型和批量正文获取保持关闭，待真实准确率数据和安全 ADR 完成后再逐项开放。
