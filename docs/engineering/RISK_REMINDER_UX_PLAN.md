# 开发类与办公类风险提醒：设计与开发计划

更新时间：2026-08-26

## 目标

让普通用户能在几秒内回答三个问题：发生了什么、为什么需要我处理、我下一步可以做什么。

风险提醒不只显示一个等级，而是同时表达：

1. 结果是否可以接受；
2. 是否真的发现问题；
3. 当前缺少哪类证据；
4. 点击动作会造成什么影响。

## 用户可见状态

| 状态 | 适用条件 | 用户动作 |
| --- | --- | --- |
| 可以确认 | 独立复核通过且验证通过 | 查看结果后确认交付 |
| 等待复核 | 结果已生成，独立复核仍在运行 | 等待，不要求用户重复操作 |
| 需要返工 | 有明确复核问题或验证失败 | 查看文件/行号/失败输出后让 AI 修复 |
| 需要补验证 | 没有配置或执行可复现验证 | 配置并执行验证，不把证据缺失当成代码缺陷 |
| 复核结论不一致 | 状态为需修改，但没有问题项且摘要为正面 | 查看完整复核或重新复核，不盲目重写 |

“高风险”只用于有明确阻塞问题的结果。证据缺失使用“需要补验证”，结论矛盾使用“复核结论不一致”。这两类状态使用警告色，不使用确认缺陷的红色。

## 领域差异

### 开发类

- 执行前：显示工作区、变更权限、预计影响和验证命令。
- 结果后：显示变更文件、独立代码复核问题、测试/类型检查/构建结果。
- 应用前：明确“应用到本地基础分支”和“创建 Pull Request”的区别。
- 没有验证命令时，只能提示证据不足，不能声称代码已经失败。

### 办公类

- 只读查询、分析和预览尽量不弹出高打扰确认。
- 写入前显示目标文件、记录数量、字段范围、资料版本和是否可撤销。
- 批量修改、覆盖、删除、对外发送、付款和权限变化必须独立强确认。
- 失败时显示已完成数量、失败数量、回滚状态和人工处理要求。

## 页面结构

结果卡片按以下顺序展示：

```text
工作类型 → 结果状态 → 风险等级
为什么这样判断
完成了什么 | 检查结果 | 建议下一步
```

技术详情继续保留在完整报告和专业详情中；普通用户首先看到可执行的下一步，不需要理解 Worktree、Invocation 或内部 ID。

## 开发计划

### 第 1 阶段：结果提醒模型（已完成）

- 增加开发交付、办公资料处理、其他任务三类标识。
- 区分明确问题、验证证据缺失和复核结论矛盾。
- 复核摘要为正面但 verdict 为需修改时，阻止盲目返工并提示重新复核。
- 办公类不再复用“写入代码基础分支”的确认文案。

### 第 2 阶段：证据与复核数据（已完成）

- 服务端详情已提供 `deliveryEvidence`：统一返回复核状态、问题项计数、结论一致性、验证状态、命令、退出码和有限失败摘要。
- 应用前预览已绑定当前 Worktree、分支、变更文件和复核提交，并由服务端计算是否允许继续。
- 交付接口在证据未通过时返回明确的 `409 work_item_delivery_evidence_not_ready`，不依赖前端按钮实现安全门禁。
- 验证缺失、验证失败、复核待完成、复核矛盾和明确需修改已使用不同机器状态码。
- 复核必须返回结构化 verdict；只要 verdict 为需修改就会阻断交付，即使问题列表暂时为空也不会降级成“等待复核”。
- 验证必须同时具备 `verified: true` 与 `passed: true`；只有 `passed` 声明、未配置命令或验证设施异常都不能形成通过证据。
- 将“复核通过”“验证通过”“人工确认”三个事实分开记录。
- 当复核状态和摘要矛盾时，记录异常事件并支持一次受控重试。

### 第 3 阶段：领域化动作体验（已完成）

- 开发类已具备“查看变更”“补跑验证”“让 AI 修复”“确认并创建 PR”动作分流；不可用动作会按当前状态禁用，避免误触发。
- 已创建 PR 的开发任务可以在原工作区和原分支继续修复；旧 PR 证据进入历史，重新复核和验证通过后再恢复受控交付，不因已有 PR 丢失修复闭环。
- 已有 PR 的返工交付会先推送当前分支最新提交，再复用现有 PR；动作预览明确区分“创建 PR”和“更新 PR”。
- 办公类已具备文件/记录/字段范围和可撤销性预览，并展示批次成功/失败数量、回滚状态和折叠的逐条详情。
- 办公批次数量区分当前生效、已恢复、失败、待处理和状态未知；目标文件取明确写入对象，不再把所有输入附件都算作修改目标。
- 办公成果类型与交付通道分开表达：办公文件也可以通过 PR 交付，确认文案以真实交付通道为准。
- 部分成功、存在失败项、回滚中或已回滚的办公批次不能被“复核通过 + 文件验证通过”误判为可应用；服务端证据和前端确认按钮使用同一阻断状态。
- 高风险外部动作继续使用独立确认，不被普通任务确认隐式放行。

### 第 4 阶段：验收与发布（进行中）

- 单元测试覆盖五种用户可见状态及办公批次证据投影。
- Web 测试覆盖开发交付动作按钮、不可用原因和办公批次成功/失败/回滚详情；办公文件处理、无验证命令和矛盾复核已有回归覆盖。
- 真实服务端编码 E2E 已覆盖执行、验证、独立复核和受控交付证据，正式命令从仓库根目录运行以加载评审器配置。
- 真实用户验收关注：用户能否说出阻塞原因、下一步和点击后影响。
- 已完成定向服务端/Web 测试、类型检查、Web 生产构建和真实服务端编码 E2E；待完成真实用户验收和最终全量 P4.14 发布门禁。

## 后续治理接口

- Ledger 内部已支持批次提交失败后的自动补偿，以及进程中断后的继续提交；普通任务页暂不直接调用底层 `approved: true` 接口。
- 若要增加“重试失败项”，应提供绑定工作项、批次 ID、最新 revision 和一次性审批授权的专用服务端接口，并在成功后刷新结构化交付证据。
- 若要增加“人工回滚”，应先补充持久化回滚快照的保留策略、可回滚窗口、冲突检测和独立确认；没有这些条件时只展示回滚事实，不显示不可执行的按钮。

## 验收标准

- 用户不需要阅读原始 AI 报告，就能理解当前是否可接受。
- “高风险”出现时，页面能展示具体阻塞原因。
- 没有验证命令时，不显示为已发现代码缺陷。
- 复核结论矛盾时，不自动让 AI 重写，也不允许直接放行。
- 开发类和办公类的确认动作不混用。
- 所有动作保留原结果、复核记录和可追溯证据。
